Cómo preparar el test.c de cada módulo

Cada módulo cXX lleva un runner de tests propio en cXX/test/test.c: un único fichero C, sin dependencias, que compila cada ejercicio del repo con -Wall -Wextra -Werror, lo ejecuta en un proceso hijo y compara la salida byte a byte. Aquí se explica cómo se usan, cómo están hechos por dentro y cómo preparar el tuyo para un módulo nuevo.

1Estructura de directorios

El runner busca los ejercicios en una raíz que llamamos repo. Acepta las dos estructuras habituales, y la detecta solo:

# En el campus (repo clonado dentro del módulo):
c06/
├── repo/
│   ├── ex00/ft_print_program_name.c
│   └── ex01/ft_print_params.c
└── test/
    └── test.c

# En este repositorio (ejercicios directamente en el módulo):
c/c06/
├── ex00/ft_print_program_name.c
├── ex01/ft_print_params.c
└── test/
    └── test.c

El orden de detección es: repo/ex00 → ex00 (raíz .) → ../repo/ex00 → ... Y siempre puedes forzarla pasándola como argumento: ./test/runner /ruta/al/repo.

Por qué un runner en C y no un script — En el campus no siempre tienes python3 ni permisos para instalar nada, pero cc está garantizado. Un solo test.c sin dependencias se compila y corre en cualquier máquina de 42. Además, con fork + execv el runner controla argv, el stdin y el tiempo de ejecución del programa probado — cosas que un script hace peor o no hace.

2Compilar y ejecutar el runner

cd c06                                             # el módulo que sea
cc -Wall -Wextra -Werror -o test/runner test/test.c
./test/runner                # autodetecta el repo
./test/runner repo           # o dile dónde está
./test/runner repo --extra   # c06: activa también los tests no portables

La salida es una línea por caso — [OK], [KO] o [SKIP] — y un resumen final. Si un caso falla verás el argv usado, la salida esperada y la obtenida (con los \n visibles como escapes), y si el programa murió por señal (segfault) o devolvió un exit code raro:

[KO]   ex03  orden ASCII no alfabetico
       esperado: "0\nAbc\nabc\nz\n"
       obtenido: "Abc\n0\nabc\nz\n"

14 OK  1 KO  0 SKIP

El runner devuelve exit code 1 si algo falla y 0 si todo pasa, así que sirve para un hook de git o un CI. Un ejercicio cuyo fichero fuente no existe todavía sale como [SKIP], no como fallo: puedes tener la tabla completa desde el día uno e ir haciendo ejercicios.

Para lanzar los 14 módulos de golpe está c/run_tests.sh:

bash c/run_tests.sh            # todos
bash c/run_tests.sh c06 c12    # solo los que pidas

3Anatomía del runner

Todos los test.c comparten el mismo esqueleto (el de referencia es c00/test/test.c). Tiene tres piezas:

1. La tabla de casos — un array g_cases[] donde cada entrada describe un test: qué ejercicio, qué fuentes compilar, qué main de prueba usar y qué salida esperar:

typedef struct s_case
{
	const char	*ex;        /* "ex00" (para mensajes)                  */
	const char	*desc;      /* descripción corta                        */
	const char	*srcs;      /* fuentes relativas al repo, sep. espacio  */
	const char	*inc;       /* dir para -I relativo al repo, o NULL     */
	const char	*main_src;  /* main de test embebido como literal       */
	const char	*expected;  /* stdout esperado; NULL = usar gen()       */
	char		*(*gen)(void);  /* genera esperados largos en runtime   */
}	t_case;

2. La fase de compilación — para cada caso, el runner escribe main_src en un main.c dentro de un directorio temporal (mkdtemp en /tmp), y lo compila junto a las fuentes del repo:

cc -Wall -Wextra -Werror [-I repo/inc] repo/exNN/fuente.c main.c -o /tmp/.../prog

Si no compila, el caso es [KO] y se vuelca el log del compilador. El repo nunca se ensucia: todo ocurre en el temporal, que se borra al final.

3. La fase de ejecución — fork(), en el hijo se redirige stdout a un pipe con dup2, se arma alarm(5) (mata bucles infinitos) y se hace execv. El padre lee todo el pipe, espera con waitpid y compara con strcmp contra lo esperado. Señal recibida o salida distinta → [KO].

Los ejercicios son funciones; el main lo pone el test — En casi todos los módulos tú entregas una función (ft_strlen, ft_swap…) sin main. El runner aporta uno por caso, embebido como literal de cadena: declara el prototipo, llama a la función con los argumentos del caso e imprime el resultado por stdout. Así cada caso decide exactamente qué observa. La excepción son los módulos de programas (c06, c10, el do-op de c11): ahí no hay main que inyectar y lo que se controla es argv — ver §6.

4Preparar el test.c de un módulo nuevo

Receta, partiendo del runner plantilla:

1. mkdir -p cXX/test
2. cp c00/test/test.c cXX/test/test.c
3. Edita la cabecera del fichero (nombre del módulo).
4. Cambia el prefijo del temporal:  "cXXtest.XXXXXX"
   (en main: strcpy(g_tmp, "/tmp/cXXtest.XXXXXX"))
5. Sustituye la tabla g_cases[] por los casos de tu módulo.
6. Compila el runner y pásalo; itera hasta ver 0 KO.

El núcleo (utilidades, compilación, ejecución, colores, resumen) no se toca: solo cambian la cabecera, el prefijo del temporal y la tabla. Si el módulo necesita algo que la struct no cubre (argv por caso, stdin, stderr…), se extiende la struct con un campo más — es lo que hacen c06, c09, c10 y c11 — pero el formato de salida y el resto del esqueleto se mantienen idénticos.

5Añadir casos y ejercicios

Un caso nuevo es una línea más en g_cases[]. Por ejemplo, para probar ft_strlen de c01/ex06:

{"ex06", "strlen basico", "ex06/ft_strlen.c", NULL,
	"#include <stdio.h>\n"
	"int ft_strlen(char *s);\n"
	"int main(void){printf(\"%d %d\", ft_strlen(\"\"), "
	"ft_strlen(\"hola mundo\"));return 0;}\n",
	"0 10", NULL},

Reglas prácticas:

· srcs admite varias fuentes: "ex02/ft_list_size.c ex00/ft_create_elem.c"
· inc añade un -I:            inc = "ex00"  →  -I repo/ex00  (headers como ft_list.h)
· expected = NULL + gen       →  el esperado se calcula en runtime (salidas largas:
                                  las 120 combinaciones de print_comb, un hexdump…)
· el main embebido es un literal C: las comillas van escapadas (\")
  y un salto de línea que el main deba IMPRIMIR se escribe \\n
  (un \n a secas es un salto en el fichero main.c generado, no en la salida)

Piensa cada caso como una pregunta concreta: el caso «param vacío» de c06/ex01 pilla a quien usa if (argv[i][0]) de guarda; el «orden ASCII» de c06/ex03 pilla el sort alfabético; los límites INT_MIN/INT_MAX de ft_putnbr pillan el overflow de -n. Los casos que solo repiten el enunciado no cazan nada.

6Particularidades de cada módulo

MóduloTipoQué tiene de especial su test.c
c00funcionesEs la plantilla. Esperados largos con gen(): las combinaciones de print_comb/comb2/combn se generan en runtime en vez de incrustar constantes de 40 KB.
c01funcionesTabla directa: punteros, swap, div_mod, tablas de int.
c02funcionesft_print_memory imprime direcciones reales: el runner recorta el prefijo <hex>:  de cada línea antes de comparar, y el modelo (hex + ascii con .) se calcula con gen().
c03funcionesTabla directa: strcmp/strcat/strstr/strlcat.
c04funcionesCasos sucios de ft_atoi/atoi_base (signos múltiples, espacios, bases inválidas) y límites de int.
c05funcionesRecursivos vs iterativos, overflow de factorial, sqrt de no-cuadrados, primos.
c06programasNo hay main que inyectar: cada caso define su argv completo, argv[0] incluido — con execv puedes mentir en el nombre (pouic, ruta absoluta) y cazar al que lo lleva hardcodeado. El caso argc == 0 no es portable y solo corre con --extra.
c07funcionesTodo devuelve memoria de malloc: los mains liberan lo que reciben, y conviene pasar el runner también bajo valgrind (§7).
c08headersSe entrega un .h, no un .c: el main se compila solo con -I al directorio del ejercicio (casos header-only). La existencia se comprueba sobre el propio .h.
c09make / libftCopia las fuentes a un temporal y ahí ejecuta libft_creator.sh y el Makefile: all, clean (borra los .o, conserva libft.a), fclean, re; verifica con nm que la librería exporta los cinco ft_* y enlaza un main contra ella.
c10programasCrea ficheros de prueba en el temporal (texto, binario, vacío, sin permisos con chmod 000) y compara contra referencias calculadas en el propio runner (equivalentes a cat/tail -c/hexdump). Captura también stderr y el exit code, y alimenta stdin por pipe para ft_cat.
c11mixtoex00–ex07 son funciones normales, pero do-op (ex05) es un programa de varias fuentes: se compila una vez y se ejecuta con una batería de argv (operador desconocido, división por cero, basura en los números…).
c12funciones + headerTodos los mains incluyen ft_list.h (inc = "ex00") y enlazan ex00/ft_create_elem.c además de la fuente del ejercicio. Helpers mk() para montar listas en cada main.
c13funciones + headerIgual que c12 con ft_btree.h y btree_create_node.c; los mains comparten un árbol de prueba fijo (1..7, raíz 4) para que los recorridos prefix/infix/suffix tengan esperados conocidos.

7Consejos y trampas conocidas

El escapado es la trampa número uno. El main de test vive dentro de un literal de C: toda comilla del main va como \", y hay dos niveles de \n. Si el main debe imprimir un salto, en el literal exterior se escribe \\n; un \n simple solo formatea el main.c generado. Si un esperado no cuadra por un salto de más o de menos, empieza por aquí — por eso el runner imprime los escapes visibles.

SKIP no es un error. Prepara la tabla completa del módulo antes de hacer los ejercicios: los que falten saldrán [SKIP] y se irán encendiendo solos según entregues ficheros.

El runner no pasa norminette, y no tiene que pasarla. Es herramienta, no entregable: no se entrega, no se corrige. Lo que sí debe compilar limpio con -Wall -Wextra -Werror es el propio runner (prueba de fuego de tus prototipos) y, por supuesto, cada ejercicio.

Memoria: en los módulos con malloc (c07, c12, c13) el runner comprueba comportamiento, no fugas. Para fugas, pasa el binario del caso bajo valgrind a mano:

valgrind --leak-check=full ./test/runner    # los hijos heredan valgrind con --trace-children=yes

No toques el repo desde el test. Todo lo que el runner genera (mains, binarios, logs, ficheros de prueba, la libft de c09) vive en el directorio de mkdtemp y muere con cleanup(). Si un test necesita un fichero, lo crea en el temporal — nunca junto a los ejercicios.

La moraleja — Escribir el tester te hace mejor que el tester: para diseñar el caso «¿y si argv[0] miente?» tienes que entender execv; para el caso «orden ASCII» tienes que saber por qué '0' < 'A' < 'a'. Cada caso que se te ocurra es un bug que ya no escribirás. En la piscine el tester eres tú.
