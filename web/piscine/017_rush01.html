C Piscine — Rush 01

El puzle de los rascacielos (skyscrapers): rellenar una cuadrícula N×N con alturas de 1 a N sabiendo cuántos edificios se ven desde cada borde. El primer problema de la piscine que no se resuelve con una fórmula, sino probando — y que obliga a pensar en cuánto cuesta probar.

  • Entrada — validar y leer las pistas
  • Contar edificios visibles
  • ft_ordcom — la permutación número k
  • ft_skyline_isolver — backtracking por filas
  • Columnas: solo al final
  • ft_putmatrix — la salida
  • Ojo: límites y coste
El puzle — Cada casilla es un edificio de altura 1…N; en cada fila y en cada columna no se repite ninguna altura (es un cuadrado latino). Alrededor de la cuadrícula hay 4N pistas: cuántos edificios ve alguien que mira desde ese borde, teniendo en cuenta que uno alto tapa a los bajos que tiene detrás. El programa recibe las pistas en un solo argumento, en este orden: columnas vistas desde arriba, columnas desde abajo, filas desde la izquierda y filas desde la derecha. Si hay solución la imprime; si no, Error. 
$> ./rush-01 "4 3 2 1 1 2 2 2 4 3 2 1 1 2 2 2"
1 2 3 4
2 3 4 1
3 4 1 2
4 1 2 3
El enunciado clásico es de 4×4; este grupo lo generalizó para que el tamaño salga del número de pistas (de 3×3 en adelante). No hay PDF del enunciado en el pack. Es trabajo de grupo: la cabecera de rush01.c la firma otra persona del grupo; el repo vive en packs/piscine/017_rush01/repo/ex00/.

entradaft_is_valid_arg y ft_parse_arg

Entrega: ex00/ft_is_valid_arg.c, ex00/ft_parse_arg.cUsa: write

La validación es una pequeña máquina de dos estados: check vale 0 cuando se espera un dígito y 1 cuando se espera un espacio. Así se aceptan solo dígitos sueltos separados por un espacio. El número de pistas tiene que ser múltiplo de 4, y el tamaño es ese número dividido entre 4.

	while (*str)
	{
		if (('1' <= *str && *str <= '9') && !check)
		{
			length++;
			check = 1;
			str++;
		}
		else if (*str == ' ' && check)
		{
			check = 0;
			str++;
		}
		else
			break ;
	}
	if (length % 4 == 0)
		return (length / 4);
	return (0);

Después, ft_parse_arg vuelca los dígitos en int inp[4][9]: una fila por borde (arriba, abajo, izquierda, derecha) y size pistas en cada una. Aquí sí se comprueba que ninguna pista pase de size.

		if (j >= size)
		{
			j = 0;
			i++;
		}
		if ('1' <= *str && *str <= ('0' + size))
		{
			inp[i][j] = *str - 0x30;
			j++;
		}
Qué te obliga a aprender — Que validar la entrada es la mitad del programa. Un parser con estado (check) es la forma más simple de reconocer un formato, y es el germen de los autómatas que aparecerán más adelante (minishell, por ejemplo). Y que las tablas de tamaño fijo ([4][9]) imponen un tope que hay que defender en main.

vistasft_check_row_left / right, ft_check_col_top / bottom

Entrega: ex00/ft_check_row.c, ex00/ft_check_col.cUsa: write

Contar cuántos edificios se ven es llevar el máximo visto hasta ahora: cada vez que aparece uno más alto que todos los anteriores, se ve, y pasa a ser el nuevo máximo. Las cuatro funciones son la misma idea recorriendo en cuatro sentidos; para mirar desde la derecha o desde abajo se lee el índice al revés (size - i - 1).

	while (i < size)
	{
		if (max < pos[p][i])
		{
			max = pos[p][i];
			count++;
		}
		i++;
	}
	if (count == inp[2][p])
		return (1);
Qué te obliga a aprender — A traducir una regla del mundo real («uno alto tapa a los de detrás») a un invariante de bucle: «max es el edificio más alto visto hasta i». Escribir la misma función cuatro veces cambiando solo el recorrido también deja ver el coste de no tener todavía punteros a función (C11).

claveft_ordcom — la permutación número k

Entrega: ex00/rush01.c, ex00/ft_factorial.cUsa: write

La pieza más original del rush. Una fila válida es una permutación de 1…N, y hay N! de ellas. En vez de generarlas con recursión, el grupo las numera: dada una i entre 0 y N!−1, ft_ordcom construye directamente la permutación que ocupa ese puesto en orden lexicográfico. ava marca qué alturas están ya usadas (0 = libre).

	j = 0;
	while (j < size)
	{
		t = i / ft_factorial(size - 1 - j);
		i_ava = 0;
		while (i_ava < size && t >= 0)
		{
			if (ava[i_ava] == 0)
				t--;
			i_ava++;
		}
		ava[i_ava - 1] = 1;
		pos[p][j] = i_ava;
		i = i % ft_factorial(size - 1 - j);
		j++;
	}

Es el sistema factorial de numeración: en la posición j, el cociente i / (N−1−j)! dice cuál de las alturas que quedan libres va ahí, y el resto pasa a la posición siguiente. Por ejemplo, con N = 4 e i = 10:

posicióncocientelibreseligeresto
010 / 3! = 11 2 3 4la 2.ª → 210 % 6 = 4
14 / 2! = 21 3 4la 3.ª → 44 % 2 = 0
20 / 1! = 01 3la 1.ª → 10
30 / 0! = 03la 1.ª → 30

La permutación número 10 es 2 4 1 3. ft_setcom solo prepara ava (libres las size primeras, ocupadas el resto) antes de llamar a ft_ordcom.

Qué te obliga a aprender — Que se puede numerar un espacio de búsqueda: si sabes contar las soluciones posibles (N!), puedes recorrerlas con un simple entero en lugar de con estructuras. Es la misma idea que hay detrás de convertir un número de base 10 a otra base (C04), solo que aquí cada cifra tiene su propia base. De paso, el ejercicio de factorial de C05 deja de ser un ejercicio y se convierte en herramienta.

solverft_skyline_isolver — backtracking por filas

Entrega: ex00/rush01.cUsa: write

La recursión va fila a fila (p). Para la fila actual prueba las N! permutaciones; si una cumple las pistas de izquierda y derecha, baja a la fila siguiente. Si desde ahí se llega a una solución, devuelve 1 hacia arriba sin probar más; si no, sigue con la siguiente permutación de esta fila.

	while (i_com < ft_factorial(size) && p < size)
	{
		ft_setcom(pos, size, i_com, p);
		if (ft_check_row_left(inp, size, pos, p)
			&& ft_check_row_right(inp, size, pos, p))
		{
			r = ft_skyline_isolver(inp, size, pos, p + 1);
			if (r == 1)
				return (r);
		}
		i_com++;
	}
	if (p == size)
		r = ft_check_col(inp, size, pos) && ft_diff_col(pos, size);
	else
		r = 0;
	return (r);

Cuando p == size el bucle ni entra: todas las filas están puestas y lo que queda es comprobar las columnas. Ese es el caso base.

Qué te obliga a aprender — El esqueleto del backtracking: elegir, comprobar, bajar un nivel y, si falla, deshacer y probar la siguiente opción. Aquí «deshacer» es gratis porque la fila p se sobrescribe con la siguiente permutación. Es el mismo patrón que ft_print_combn (C00) o las diez reinas (C05), ahora con poda: las filas que no cumplen sus pistas cortan una rama entera.

finalColumnas: ft_check_col y ft_diff_col

Entrega: ex00/ft_check_col.c, ex00/ft_diff_col.cUsa: write

Las filas no repiten alturas por construcción (son permutaciones), pero las columnas sí podrían. ft_diff_col compara cada casilla con todas las de debajo en su columna, y ft_check_col comprueba las pistas de arriba y de abajo. Las dos se ejecutan solo cuando la cuadrícula está completa.

			z = i + 1;
			while (z < size)
			{
				if (pos[i][j] == pos[z][j] && i != z)
					return (0);
				z++;
			}

(El i != z sobra: z empieza en i + 1.)

Qué te obliga a aprender — Dónde poner cada comprobación es una decisión de diseño con consecuencias de rendimiento. Comprobar las columnas al final es lo más sencillo de escribir, pero significa que una columna con dos alturas iguales en las dos primeras filas no se detecta hasta haber rellenado todas las demás.

salidaft_putmatrix y main

Entrega: ex00/ft_putmatrix.c, ex00/rush01.cUsa: write

ft_putmatrix escribe cada altura como dígito, con espacio entre columnas y salto de línea al final de la fila. main encadena todo y responde Error (con código de salida 1) si falta el argumento, si el número de pistas no cuadra o si no hay solución.

	size = ft_is_valid_arg(argv[1]);
	if (size < 3 || size > 10)
	{
		write(1, "Error\n", 6);
		return (1);
	}
	ft_parse_arg(inp, argv[1], size);
	if (ft_skyline_isolver(inp, size, sol, 0))
		ft_putmatrix(sol, size);
Qué te obliga a aprender — A separar el programa en piezas que se pueden probar solas (parsear, resolver, imprimir) y repartirlas en el grupo. Ocho ficheros para un rush de fin de semana es justo eso: cada persona se lleva una pieza, pero en la defensa hay que saber explicar las de los demás.

ojoLímites y coste

Probado: 3×3, 4×4 y 5×5 resuelven al instante; 6×6 no termina en 60 s
  • Tope de tamaño. Ojo: main acepta size hasta 10, pero las tablas son de 9 (inp[4][9], pos[9][9]). Con 40 pistas, ft_parse_arg escribe fuera de inp (AddressSanitizer lo marca como stack-buffer-overflow). La comprobación debería cortar en 9.
  • 9×9. En ft_ordcom, while (ava[size] == 0) size++; busca el primer 1 que puso ft_setcom; con tamaño 9 no hay ninguno dentro del array y la lectura sigue en ava[9], fuera de rango.
  • Retorno ignorado. ft_parse_arg devuelve 0 si una pista pasa de size, pero main no lo mira: el resto de inp queda sin inicializar. En la práctica sale Error porque no hay solución, pero es por casualidad.
  • Coste. Cada fila prueba N! permutaciones y las columnas solo se miran al final, así que en el peor caso son (N!)N cuadrículas: 244 ≈ 330 000 para 4×4, pero 7206 ≈ 1,4·1017 para 6×6. La poda por filas salva el 5×5; el 6×6 ya no. Además ft_factorial se recalcula en cada vuelta del bucle.
  • Restos. En ft_factorial.c queda comentada una versión con los valores a mano, donde 8! y 9! están mal (40200 y 361800; son 40320 y 362880). No se usa, pero se entrega.
Qué te obliga a aprender — Que «funciona con el ejemplo» no es lo mismo que «funciona». Generalizar de 4×4 a N×N es buena idea, pero trae dos obligaciones: que los límites de las tablas coincidan con los que acepta main, y que el algoritmo aguante el crecimiento. Las factoriales crecen más deprisa que cualquier ordenador.
