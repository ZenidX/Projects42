C Piscine — Rush 02

Un programa que escribe números con letras: 42 → forty two. Las palabras no están en el código, salen de un diccionario en un fichero que se puede cambiar. Es el primer programa de la piscine que lee un fichero, lo parsea, guarda lo leído en memoria dinámica y lo libera todo.

  • main — argumentos y entrada estándar
  • ft_read_file — el fichero entero en una cadena
  • ft_parse_dict — de texto a tabla
  • write_num — grupos de tres cifras
  • write_group — de 1 a 999
  • ft_write_nbr — dos pasadas
  • Memoria y Makefile
  • Ojo: lo que no cumple
El enunciado — Ejecutable rush-02, compilado con un Makefile (reglas $(NAME), clean y fclean). Con un argumento, es el número; con dos, el primero es otro diccionario. Si el número no es un entero sin signo, Error; si el diccionario está mal o no basta para escribir el número, Dict Error. Y una frase en recuadro: «vuestro programa debe ir más allá de unsigned int». El diccionario tiene líneas número : palabra, con espacios opcionales que hay que recortar: 
$> ./rush-02 42
forty two
$> ./rush-02 100000
one hundred thousand
$> ./rush-02 10.4
Error
Como bonus se puede añadir «and» y guiones, otro idioma con otro diccionario, o leer números de la entrada estándar si el argumento es -. Este grupo hizo el último. Trabajo de grupo; el código está en packs/piscine/018_rush02/repo/ex00/.

mainmain, get_args y read_stdin

Entrega: ex00/rush02.c, ex00/rush02.hAutorizado: write, malloc, free, open, read, close

El orden de main es: decidir qué es diccionario y qué es número, validar el número antes de abrir el diccionario, cargar el diccionario y escribir.

	get_args(argc, argv, &dict_name, &num);
	if (!is_stdin(num) && !ft_is_positive(num))
	{
		ft_putstr("Error\n");
		return (0);
	}
	dict = ft_read_dict(dict_name);
	if (dict == NULL)
	{
		ft_putstr("Dict Error\n");
		return (0);
	}
	if (is_stdin(num))
		read_stdin(dict);
	else
		ft_write_nbr(num, dict);
	ft_free_dict(dict);

El bonus de la entrada estándar reutiliza piezas: ft_read_file(0) lee del descriptor 0 igual que de un fichero, y ft_split(content, "\n") lo trocea en líneas. Cada línea se valida y se escribe por separado.

$> printf "42\n7\n\n1000001\n" | ./rush-02 -
forty two
seven
one million one
Qué te obliga a aprender — Que la entrada estándar es un descriptor más (el 0). Si ft_read_file recibe un fd en vez de un nombre de fichero, el bonus sale casi gratis. Y que el número nunca se convierte a int: se valida y se trata como cadena de dígitos, que es la única forma de «ir más allá de unsigned int» sin tipos grandes.

leerft_read_file y ft_strcat

Entrega: ex00/ft_read_dict.c, ex00/ft_strutils.cAutorizado: read, malloc, free

No se sabe de antemano cuánto mide el fichero, así que se lee a trozos de 254 bytes y se va pegando cada trozo a lo acumulado. El ft_strcat de este rush no es el de la libc: devuelve un bloque nuevo y libera el primero, pensado para usarse como s = ft_strcat(s, trozo). Por eso la cadena inicial es una cadena vacía del heap y no el literal "".

	dict_str = ft_strifcpy("", 0, 0);
	n = read(fd, buffer, sizeof(buffer) - 1);
	while (n > 0)
	{
		buffer[n] = '\0';
		dict_str = ft_strcat(dict_str, buffer);
		n = read(fd, buffer, sizeof(buffer) - 1);
	}
	if (n == -1)
	{
		free(dict_str);
		return (0);
	}
Qué te obliga a aprender — read no lee «el fichero»: lee como mucho n bytes y te dice cuántos ha leído (0 al final, −1 si falla). El sizeof(buffer) - 1 reserva el hueco del '\0' para poder tratar cada trozo como cadena. Y la regla de propiedad de memoria: una función que libera su argumento tiene que decirlo, porque quien la llame con un literal se lleva un free inválido. El comentario del código lo deja escrito.

parseft_parse_dict y ft_outspace

Entrega: ex00/ft_read_dict.c, ex00/ft_split.cAutorizado: malloc, free

El texto se convierte en un array de t_dict (pares nbr / word, ambos cadenas) terminado en una entrada con nbr a 0, igual que argv termina en NULL. Primero se parte por '\n' (las líneas vacías desaparecen solas en el split), luego cada línea por ':'. Si no salen exactamente dos trozos, es un Dict Error.

	while (dict_lines[i])
	{
		dict_split = ft_split(dict_lines[i], ":");
		if (ft_arrlen(dict_split) != 2)
			return (ft_parse_error(dict, dict_lines, dict_split, i));
		dict[i].nbr = ft_outspace(dict_split[0]);
		dict[i].word = ft_outspace(dict_split[1]);
		ft_free_split(dict_split);
		i++;
	}
	dict[i].nbr = 0;
	dict[i].word = 0;

ft_outspace recorta espacios por los dos extremos moviendo dos índices hacia dentro, y copia lo que queda con ft_strifcpy(str, ini, fin), que reserva y copia el trozo [ini, fin). El camino de error, ft_parse_error, pone el centinela en la entrada i para que ft_free_dict sepa hasta dónde liberar.

Qué te obliga a aprender — A diseñar una estructura de datos propia (el struct de C11 en un caso real) y a decidir cómo se sabe dónde acaba un array dinámico: aquí con un centinela. Y que el camino de error también tiene que liberar todo lo reservado hasta ese momento, que es donde suelen aparecer las fugas.

clavewrite_num, group_value y scale_key

Entrega: ex00/ft_write_nbr.c, ex00/ft_write_utils.cAutorizado: write

Así se leen los números en inglés (y en español): en grupos de tres cifras, cada uno seguido de su escala. 123456789 es «123 million, 456 thousand, 789». El número nunca pasa a entero: exp es la potencia de 10 del grupo (0, 3, 6…), y group_value saca las tres cifras de esas posiciones de la cadena. Esas sí caben en un int, porque nunca pasan de 999.

	len = ft_strlen(nbr);
	exp = ((len + 2) / 3 - 1) * 3;
	while (exp >= 0)
	{
		v = group_value(nbr, len, exp);
		if (v > 0)
		{
			if (!write_group(v, dict, do_write, first))
				return (0);
			if (exp > 0)
			{
				if (!put_word(dict, scale_key(buf, exp), do_write, first))
					return (0);
			}
		}
		exp -= 3;
	}

Para buscar la escala en el diccionario no hace falta calcular 10exp: scale_key escribe la clave como texto, un '1' y exp ceros. Las claves del diccionario son cadenas y se comparan con ft_strcmp, así que "1000000000000000000000000000000000000" (undecillion) funciona igual que "1000". Los grupos a cero se saltan enteros: por eso 1000000 da one million y no «one million zero thousand».

Qué te obliga a aprender — Que un número es una representación: si el problema no pide aritmética, no hace falta convertirlo, y trabajar con los dígitos como texto elimina el límite de tamaño. Es la misma descomposición posicional de ft_putnbr (C00), pero de tres en tres cifras y sin división.

grupowrite_group y find_word

Entrega: ex00/ft_write_nbr.c, ex00/ft_write_utils.cAutorizado: write

Un grupo de 1 a 999: las centenas como «cifra + hundred», y para los dos últimos dígitos primero se busca el número entero en el diccionario. Del 0 al 20 y las decenas tienen clave propia; si no está (21, 47…), se compone con decena + unidad.

	if (d >= 100)
	{
		if (!put_word(dict, ft_itokey(buf, d / 100), do_write, first))
			return (0);
		if (!put_word(dict, "100", do_write, first))
			return (0);
	}
	r = d % 100;
	if (r == 0)
		return (1);
	if (find_word(dict, ft_itokey(buf, r)))
		return (put_word(dict, ft_itokey(buf, r), do_write, first));
	if (!put_word(dict, ft_itokey(buf, (r / 10) * 10), do_write, first))
		return (0);

Buscar primero la clave exacta tiene un efecto bonito: si alguien añade 42: the answer a un diccionario, el programa lo usa. find_word es una búsqueda lineal por la tabla, suficiente para cuarenta entradas.

Qué te obliga a aprender — A no meter datos en el código. El programa no sabe inglés: sabe la estructura de los números (centenas, decenas, escalas) y le pide las palabras al diccionario. Cambiar el fichero cambia el idioma, que es la idea detrás del bonus. La separación entre lógica y datos es la que luego verás en configuraciones, traducciones y plantillas.

salidaft_write_nbr y put_word — dos pasadas

Entrega: ex00/ft_write_nbr.cAutorizado: write

Si al diccionario le falta una palabra a mitad de número, no debería salir media frase y luego Dict Error. La solución del grupo: write_num recibe un do_write, y se llama dos veces. La primera en seco, solo comprobando que todas las claves existen; la segunda, escribiendo. put_word pone el espacio antes de cada palabra salvo la primera (first).

	while (nbr[0] == '0' && nbr[1])
		nbr++;
	...
	if (!write_num(nbr, dict, 0, &first))
	{
		ft_putstr("Dict Error\n");
		return ;
	}
	first = 1;
	write_num(nbr, dict, 1, &first);
	write(1, "\n", 1);

Los ceros de delante se saltan (007 → seven) y el cero, que no tiene grupos, se trata aparte con la clave "0".

Qué te obliga a aprender — Que una salida a medias es peor que un error limpio, y que validar todo antes de escribir nada es una técnica general (las bases de datos lo llaman transacción). También el problema de la valla de C00, otra vez: el separador va entre palabras, y la bandera first es la forma de no poner un espacio de más.

extraMemoria y Makefile

Entrega: ex00/Makefile, ex00/numbers.dictProbado con: -fsanitize=address

Todo lo que se reserva se libera: el split de líneas, cada split de línea, la cadena del fichero y el diccionario. Compilado con AddressSanitizer y probado con números normales, el cero, errores y el diccionario alternativo, no aparecen fugas. El Makefile hace que cada .o dependa también de rush02.h, para que cambiar el header recompile lo que lo usa:

%.o: %.c rush02.h
	$(CC) $(FLAGS) -c $< -o $@
Qué te obliga a aprender — El enunciado avisa de que la memoria se revisa en la evaluación. Es la primera vez que «funciona» no basta: también hay que demostrar que no se pierde nada por el camino, y para eso hay que saber, para cada malloc, quién es responsable de su free.

ojoLo que no cumple

Probado: compilado y ejecutado tal cual
  • Espacios internos. El ejemplo del enunciado tiene 20 : hey everybody ! y espera hey everybody !, con un solo espacio. ft_outspace solo recorta los extremos, así que el programa escribe hey everybody ! tal cual.
  • Dos puntos en el valor. El valor puede ser «cualquier carácter imprimible», pero la línea se parte por todos los ':': 20: a:b da tres trozos y Dict Error.
  • Números de 49 cifras o más. Ojo: write_num usa char buf[48] para la clave de escala, y scale_key escribe exp + 2 bytes sin mirar el tamaño. Hasta 39 cifras escribe el número; de 40 a 48, Dict Error como debe ser; con 49 o más, AddressSanitizer marca un stack-buffer-overflow en scale_key durante la pasada en seco.
  • Claves sin validar. No se comprueba que la parte izquierda sea un número, ni que una línea de solo espacios sea «vacía» (da Dict Error).
  • Fichero suelto. En ex00/ hay un .ft_read_dict.c.swp (copia de trabajo de vim); no está en git, así que no llega a la entrega.
Qué te obliga a aprender — A leer los ejemplos del enunciado como casos de prueba. Los dos primeros puntos están literalmente en él; el tercero es la otra cara de «ir más allá de unsigned int»: quitar un límite (el del tipo) y dejar otro escondido (el de un buffer fijo).
