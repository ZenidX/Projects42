C Piscine — BSQ

El proyecto final de la piscine: Biggest SQuare. Leer un mapa de un fichero, encontrar el mayor cuadrado sin obstáculos y pintarlo. Un programa completo, con Makefile, varios ficheros de entrada, entrada estándar, validación estricta y una Moulinette que no perdona.

  • t_map — el estado del programa
  • main — uno o varios mapas
  • ft_read_file — leer el mapa
  • ft_parse_header — la primera línea
  • ft_parse_map y ft_validate_map
  • ft_bsq_isolver — buscar el cuadrado
  • ft_print_map — pintar y escribir
  • Ojo: lo que se escapa
El enunciado — Programa bsq; funciones autorizadas open, close, read, write, malloc, free y exit. La primera línea del mapa trae el número de líneas y, como sus tres últimos caracteres, el carácter vacío, el de obstáculo y el de lleno. El programa sustituye vacíos por llenos para dibujar el mayor cuadrado posible; si hay empate, el más arriba y, entre esos, el más a la izquierda. Acepta de 1 a n ficheros (con una línea en blanco entre salidas) o, sin argumentos, un mapa por la entrada estándar. Cualquier mapa inválido es un map error.

bsq.ht_map

Entrega: bsq.hAutorizado: open, close, read, write, malloc, free, exit

Todo lo que se sabe de un mapa viaja en una sola estructura. Dos decisiones que conviene tener en la cabeza para leer el resto: map[0] es la cabecera (las filas van de map[1] a map[height]), y el mejor cuadrado se guarda como fila, columna y lado en sq[3].

/*
** obj[0] vacio, obj[1] obstaculo, obj[2] lleno (el orden de la cabecera).
** map[0] es la cabecera: las filas del mapa van de map[1] a map[height].
** sq[0] fila, sq[1] columna, sq[2] lado del mayor cuadrado encontrado.
*/
typedef struct s_map
{
	char	obj[3];
	char	**map;
	int		width;
	int		height;
	int		sq[3];
}	t_map;
Qué te obliga a aprender — A diseñar el estado antes que las funciones. Con una estructura bien pensada, cada función recibe un t_map * y la Norma (máximo cuatro parámetros) deja de ser un problema. Dejar la cabecera en map[0] evita copiar el mapa, a cambio de que todos los índices de fila empiecen en 1.

mainmain y ft_run_map

Entrega: bsq.cAutorizado: write

ft_run_map hace un mapa de principio a fin: si llega NULL (no se pudo leer o no es válido) solo escribe el error; si no, resuelve, pinta y libera. main decide de dónde vienen los mapas.

	if (argc < 2)
	{
		ft_run_map(ft_map_from_fd(0));
		return (0);
	}
	i = 1;
	while (i < argc)
	{
		if (i > 1)
			ft_putstr("\n");
		ft_run_map(ft_read_map(argv[i]));
		i++;
	}
Qué te obliga a aprender — El problema de la valla otra vez (C00): la línea en blanco va entre salidas, así que se escribe antes de cada mapa menos del primero. Y que cada mapa es independiente: un fichero que no existe en medio de la lista da su map error y el programa sigue con el siguiente.

leerft_read_file, ft_map_from_fd y ft_read_map

Entrega: ft_read_file_map.c, ft_str_utils.cAutorizado: open, read, close, malloc, free

La lectura es la misma idea que en el Rush 02 (de hecho ft_split.c es idéntico): leer a trozos de 255 bytes y pegarlos con ft_strfreecat, que devuelve un bloque nuevo y libera el anterior. La lectura está separada en dos niveles para que la entrada estándar y los ficheros compartan código: ft_map_from_fd trabaja con cualquier descriptor, y ft_read_map solo añade el open y el close.

	map_str = ft_strifcpy("", 0, 0);
	n = read(fd, buffer, sizeof(buffer) - 1);
	while (n > 0)
	{
		buffer[n] = '\0';
		map_str = ft_strfreecat(map_str, buffer);
		if (!map_str)
			return (0);
		n = read(fd, buffer, sizeof(buffer) - 1);
	}

Ojo: cada vuelta copia todo lo acumulado para añadir 255 bytes, así que el coste crece con el cuadrado del tamaño del fichero. En un mapa de 1000×1000 generado con el script del enunciado (1 MB, unas 4000 lecturas), el programa tarda unos 6 segundos, y prácticamente todo ese tiempo es la lectura: el mismo mapa con una línea de más, que se rechaza justo después de leerlo, tarda lo mismo.

Qué te obliga a aprender — Que la entrada no siempre cabe en un buffer fijo y hay que crecer bajo demanda. Y que crecer de 255 en 255 bytes copiando todo cada vez es cuadrático: con el diccionario del Rush 02 no se nota; con un mapa de un megabyte, sí. BSQ es el primer proyecto donde el rendimiento se ve sin medir.

cabeceraft_parse_header y ft_check_obj

Entrega: ft_parse_header.cAutorizado: ninguna

Los tres últimos caracteres de la primera línea son vacío, obstáculo y lleno; todo lo de delante tiene que ser dígitos. ft_check_obj exige que los tres sean imprimibles (32 a 126) y distintos entre sí, y ft_is_pos convierte una altura de 0 o negativa en 0, que es el «no válido».

	h = map->map[0];
	len = ft_strlen(h);
	if (len < 4 || !ft_only_digits(h, len - 3))
		return (0);
	map->obj[0] = h[len - 3];
	map->obj[1] = h[len - 2];
	map->obj[2] = h[len - 1];
	if (!ft_check_obj(map))
		return (0);
	map->height = ft_is_pos(ft_atoi(h));
	return (map->height != 0);

Ojo: ft_only_digits mira solo los len - 3 primeros caracteres, pero ft_atoi(h) lee la cabecera entera mientras haya dígitos. El enunciado recuerda que un dígito es un carácter válido para el mapa: con la cabecera 21ox (2 líneas, vacío '1'), ft_atoi lee 21 y el mapa sale como map error. Bastaría con no dejar que la conversión pase de len - 3.

Qué te obliga a aprender — A parsear de derecha a izquierda cuando el formato lo pide: los símbolos no se reconocen por ser «no dígitos», sino por su posición al final. Y a desconfiar de reutilizar una función (ft_atoi) cuyo contrato no coincide del todo con lo que necesitas: atoi decide sola dónde para.

validarft_parse_map y ft_validate_map

Entrega: ft_parse_map.c, ft_split.cAutorizado: malloc, free

El fichero se parte por '\n'; la cabecera tiene que ser válida y el número de líneas tiene que coincidir exactamente con lo prometido. Ese conteo, como explica el propio comentario del código, protege dos cosas: que ft_validate_map no se salga del array si faltan líneas y que no se acepten líneas de sobra.

	map->map = ft_split(map_str, "\n");
	if (!map->map || ft_arrlen(map->map) < 2)
		return (ft_parse_error(map));
	if (!ft_parse_header(map))
		return (ft_parse_error(map));
	if (ft_arrlen(map->map) != map->height + 1)
		return (ft_parse_error(map));
	return (ft_validate_map(map));

Después, todas las filas deben medir lo mismo que la primera y contener solo vacíos u obstáculos. El carácter «lleno» dentro del mapa también es error: lo pone el programa.

		if (ft_strlen(map->map[i]) != map->width)
			return (ft_parse_error(map));
		j = 0;
		while (j < map->width)
		{
			if (!ft_is_map(map->map[i][j], map))
				return (ft_parse_error(map));
			j++;
		}
Qué te obliga a aprender — Que la mitad de la nota de BSQ son mapas inválidos. La Moulinette prueba cabeceras raras, líneas desiguales, caracteres extraños y ficheros vacíos, y cada uno tiene que acabar en map error sin fugas: por eso todo camino de error pasa por ft_parse_error, que libera el split y la estructura.

claveft_bsq_isolver y ft_validate_sq

Entrega: ft_bsq_isolver.cAutorizado: ninguna

El algoritmo recorre el mapa de arriba abajo y de izquierda a derecha. En cada casilla vacía intenta hacer crecer un cuadrado con esa casilla como esquina superior izquierda, pero no desde 1: empieza en el mejor lado encontrado hasta ahora más uno. Un cuadrado igual o más pequeño no serviría de nada.

			if (map->map[i[0]][i[1]] == map->obj[0])
			{
				tmp = map->sq[2];
				while (tmp != -1
					&& tmp <= map->height - i[0]
					&& tmp < map->width - i[1])
				{
					tmp++;
					ft_validate_sq(map, i, &tmp);
				}
			}

ft_validate_sq recorre el cuadrado de lado tmp. Si encuentra un obstáculo, pone tmp a −1, lo que corta sus propios bucles y el while de fuera (si un cuadrado tiene un obstáculo, todos los mayores desde esa esquina también). Si no, y es mayor que el récord, se guarda.

			if (map->map[i[0] + j[0]][i[1] + j[1]] == map->obj[1])
				*tmp = -1;
	...
	if (map->sq[2] < *tmp)
	{
		map->sq[0] = i[0];
		map->sq[1] = i[1];
		map->sq[2] = *tmp;
	}

El desempate del enunciado sale solo: como se recorre en orden de lectura y el récord solo se sustituye con < estricto, un cuadrado del mismo tamaño encontrado más tarde (más abajo o más a la derecha) nunca reemplaza al primero. Los límites del while garantizan que el cuadrado no se salga por abajo ni por la derecha.

Qué te obliga a aprender — A razonar sobre el coste. Comprobar cada casilla con cada tamaño desde cero sería inviable; esta solución poda de dos formas (empezar por el récord + 1 y abandonar al primer obstáculo). Aun así, cada casilla vacía revisa un cuadrado de (récord + 1)² celdas, así que el coste depende de lo grande que sea la respuesta. En los mapas de prueba de 1000×1000 con obstáculos la búsqueda es rápida; lo lento es leer. Y el desempate demuestra que el orden de recorrido puede resolver una regla del enunciado sin una línea de código extra.

salidaft_fill_sq y ft_print_map

Entrega: ft_print_map.cAutorizado: write

Se pinta sobre el propio mapa (no hace falta copia) y se escribe cada fila de una vez, en vez de carácter a carácter. Si no hay ningún cuadrado posible (todo obstáculos), el lado es 0, los bucles no entran y el mapa sale tal cual.

	ft_fill_sq(map);
	i = 1;
	while (i <= map->height)
	{
		ft_putstr(map->map[i]);
		ft_putstr("\n");
		i++;
	}
Qué te obliga a aprender — Que write es una llamada al sistema y cada una cuesta. El comentario del código lo cuantifica: en un mapa de 300×300, 600 llamadas en vez de 90 000. Es la misma lección que ft_print_comb2 (C00) componiendo un buffer de 5 bytes, a otra escala.

ojoLo que se escapa

Probado: compilado y ejecutado tal cual
  • Cabecera con dígitos como símbolo. Ver la cabecera: 21ox da map error en un mapa válido.
  • Líneas vacías. ft_split funde los '\n' seguidos, así que una línea vacía desaparece en lugar de dar error. 1.ox seguido de una línea vacía y de ... se acepta como mapa de una línea.
  • Último salto de línea. Por la misma razón, un mapa cuya última línea no acaba en '\n' se acepta, aunque el enunciado dice que las líneas van separadas por saltos de línea.
  • Lectura cuadrática. Ver la lectura: unos 6 s para 1 MB.
  • Salida del error. map error va a la salida estándar. Este enunciado no dice por qué descriptor debe salir; conviene comprobar qué espera la Moulinette.
Qué te obliga a aprender — Que en un proyecto con Moulinette los casos límite no son un extra: son el examen. Un split que «limpia» las líneas vacías es cómodo para parsear, pero borra justo la información que hace falta para rechazar un mapa mal formado.
