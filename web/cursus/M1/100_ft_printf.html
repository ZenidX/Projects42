Cursus — ft_printf

Reimplementar printf con nueve conversiones (cspdiuxX%) y empaquetarla en libftprintf.a. El proyecto parece de formato de texto, pero lo que enseña de verdad es cómo una función de C puede recibir un número de argumentos que no conoce — y cómo construir una librería encima de otra.

Por qué printf — En la piscine todo salía por pantalla con write y funciones hechas a mano: ft_putnbr, ft_putstr (de ahí el subtítulo del enunciado: «porque ft_putnbr() y ft_putstr() no son suficientes»). printf es la función que todo programador de C usa a diario y casi nadie ha mirado por dentro. El enunciado prohíbe gestionar el buffer interno del printf original (cada carácter va directo con write) y solo autoriza malloc, free, write y la familia va_*; la libft sí está permitida. El resultado se compara byte a byte con el printf de verdad, valor de retorno incluido. Y una vez aprobado, ft_printf entra en tu caja de herramientas para todos los proyectos siguientes.

va_*Funciones variádicas

Entrega: ft_printf.c, ft_printf.hAutorizado: va_start, va_arg, va_copy, va_end, write

El prototipo lo fija el enunciado: int ft_printf(char const *, ...);. Los tres puntos dicen «después de format vienen cuantos argumentos quieras, del tipo que quieras». El bucle principal del usuario:

int	ft_printf(const char *format, ...)
{
	va_list	ap;
	int		count;
	int		ret;

	if (!format)
		return (-1);
	va_start(ap, format);
	count = 0;
	while (*format)
	{
		if (*format == '%' && *(format + 1))
			ret = ft_conv(*(++format), &ap);
		else
			ret = ft_print_char(*format);
		if (ret < 0)
		{
			va_end(ap);
			return (-1);
		}
		count += ret;
		format++;
	}
	va_end(ap);
	return (count);
}

Las cuatro piezas de <stdarg.h>:

  • va_list ap — el «cursor» sobre los argumentos sin nombre.
  • va_start(ap, format) — lo coloca justo después del último parámetro con nombre. Por eso una función variádica necesita al menos uno.
  • va_arg(ap, tipo) — devuelve el siguiente argumento interpretándolo como tipo y avanza. Nadie comprueba que el tipo sea el correcto: lo dice el formato.
  • va_end(ap) — cierra el recorrido. Aquí se llama en las dos salidas: la normal y la de error.

Un detalle fino: ap se pasa a ft_conv como &ap (un va_list *). Así cada va_arg que hace la función auxiliar avanza el mismo cursor que ve ft_printf. Pasar el va_list por valor y seguir usándolo después en la función que llama no es portable.

Qué te obliga a aprender — Que en C los argumentos no llevan etiqueta de tipo: en la llamada solo viajan bytes, y es el formato el que dice cómo leerlos. Si escribes %d y pasas un double, va_arg leerá basura sin quejarse — por eso el compilador avisa con -Wformat en el printf real, pero no con el tuyo (salvo que lo marques con __attribute__((format))). También aparece la promoción de argumentos por defecto: en la parte variádica de una llamada, todo char y short se convierte en int, y todo float en double. Es la razón de que %c se lea con va_arg(*ap, int) y no con char: el char nunca llega como char.

cspdiuxX%El despacho por conversión

Entrega: ft_printf.cAutorizado: va_arg
static int	ft_conv(char c, va_list *ap)
{
	if (c == 'c')
		return (ft_print_char(va_arg(*ap, int)));
	if (c == 's')
		return (ft_print_str(va_arg(*ap, char *)));
	if (c == 'p')
		return (ft_print_ptr(va_arg(*ap, void *)));
	if (c == 'd' || c == 'i')
		return (ft_print_nbr(va_arg(*ap, int)));
	if (c == 'u')
		return (ft_print_unsigned(va_arg(*ap, unsigned int)));
	if (c == 'x')
		return (ft_print_hex(va_arg(*ap, unsigned int), 0));
	if (c == 'X')
		return (ft_print_hex(va_arg(*ap, unsigned int), 1));
	if (c == '%')
		return (ft_print_char('%'));
	return (-1);
}

Cada letra decide dos cosas a la vez: con qué tipo se saca el argumento y qué función lo imprime.

Conversiónva_argImprime
%cintft_print_char
%schar *ft_print_str
%pvoid *ft_print_ptr
%d %iintft_print_nbr
%uunsigned intft_print_unsigned
%x %Xunsigned intft_print_hex (minúsculas / mayúsculas)
%%— (no consume argumento)ft_print_char('%')

Fíjate en que %% no llama a va_arg: si lo hiciera, desplazaría todos los argumentos siguientes una posición.

Ojo con dos casos fuera del enunciado. Una letra desconocida (%k) hace que ft_conv devuelva -1 y ft_printf se corta ahí devolviendo -1, con lo anterior ya escrito. Y un % suelto al final de la cadena no entra en la rama de conversión (por la comprobación *(format + 1)) y se imprime tal cual: ft_printf("abc%") escribe abc% y devuelve 4, mientras que glibc devuelve -1. Las dos situaciones son comportamiento indefinido en el estándar, así que no hay una respuesta «correcta», pero conviene saber qué hace tu versión por si sale en la evaluación.

Qué te obliga a aprender — A separar el análisis del formato de la impresión: el bucle principal no sabe nada de números ni de cadenas, solo reparte trabajo. Es la «estructura extensible» que pide el enunciado: añadir una conversión es añadir una línea aquí y una función. También deja claro que el tipo de cada argumento es un contrato entre quien escribe el formato y quien lo lee, sin red de seguridad.

returnEl valor de retorno

Entrega: ft_printf.cAutorizado: write

printf devuelve el número de caracteres escritos, o un negativo si algo falla. El usuario lo resuelve con una regla única para todas las funciones de impresión: cada una devuelve cuántos caracteres ha escrito, o -1 si write ha fallado. El bucle solo suma:

		if (ret < 0)
		{
			va_end(ap);
			return (-1);
		}
		count += ret;

Por eso ft_print_char y ft_print_str devuelven directamente lo que devuelve write (un ssize_t), y las funciones de números devuelven la longitud de la cadena que imprimen. %p suma a mano los dos caracteres de 0x (se ve abajo).

Qué te obliga a aprender — Que el valor de retorno es parte de la interfaz tanto como lo que sale por pantalla, y que los errores hay que propagarlos hacia arriba en lugar de ignorarlos. write puede fallar (por ejemplo, si cierras stdout con ./a.out >&-) y un printf serio tiene que enterarse. Definir un contrato común para todas las funciones auxiliares es lo que hace que el conteo quede en dos líneas.

%c %s %%Caracteres y cadenas

Entrega: ft_print_chars.cAutorizado: write, free (+ libft: ft_strlen)
ssize_t	ft_print_char(int c)
{
	unsigned char	chr;

	chr = (unsigned char) c;
	return (write(1, &chr, 1));
}

ssize_t	ft_print_str(char *str)
{
	if (!str)
		str = "(null)";
	return (write(1, str, ft_strlen(str)));
}

ft_print_char recibe un int (por la promoción) y lo convierte a unsigned char antes de escribir, que es exactamente lo que hace el printf real con %c. La cadena se escribe de una sola vez con su longitud, no carácter a carácter.

printf("%s", NULL) es comportamiento indefinido según el estándar, pero glibc imprime (null) y los testers lo comparan; el usuario reproduce ese resultado.

Qué te obliga a aprender — Que «imitar printf» significa imitar una implementación concreta (aquí, glibc en Linux) incluso en casos que el estándar deja abiertos. Y que la conversión a unsigned char no es decorativa: así se pasa a write exactamente un byte con el valor que pidió quien llamó.

%d %i %uNúmeros en base 10

Entrega: ft_print_nbrs.c, ft_print_chars.cAutorizado: malloc, free (+ libft: ft_itoa, ft_itoa_base)
int	ft_print_nbr(int n)
{
	return (ft_print_free(ft_itoa(n)));
}

int	ft_print_unsigned(unsigned int n)
{
	return (ft_print_free(ft_itoa_base(n, "0123456789", 10, 0)));
}

En vez de reescribir putnbr, el usuario reutiliza su libft: convierte el número en una cadena reservada con malloc y la imprime. Para no repetir el «imprimir y liberar» en cada sitio, todo pasa por un único helper:

int	ft_print_free(char *str)
{
	int	ret;

	if (!str)
		return (-1);
	ret = ft_print_str(str);
	free(str);
	return (ret);
}

Si malloc falló, la cadena es NULL y se devuelve -1. Si no, se imprime y se libera siempre, haya ido bien el write o no. Es el único free del proyecto, y por eso no hay forma de dejar un leak por un camino de error.

%d e %i usan ft_itoa, que ya gestiona el signo y INT_MIN. %u usa ft_itoa_base, una función de la piscine (C07) adaptada a unsigned long y añadida a la libft de este repo:

char	*ft_itoa_base(unsigned long n, char *base, int b, int d)
{
	char	*r;
	int		dd;

	if (n / b != 0)
		r = ft_itoa_base(n / b, base, b, d + 1);
	else
	{
		r = (char *)malloc(sizeof(char) * (d + 2));
		r = ft_char_init(r, d + 1);
	}
	if (!r)
		return (NULL);
	dd = ft_strlen(r);
	r[dd - 1 - d] = base[n % b];
	return (r);
}

El parámetro d cuenta la profundidad. La llamada más profunda (la de la cifra más significativa) ya sabe cuántas cifras hay en total, d + 1, y reserva la cadena una sola vez, rellena de '0' por ft_char_init. Luego, a la vuelta de la recursión, cada nivel escribe su cifra (n % b) en la posición que le toca, contando desde el final.

Qué te obliga a aprender — A reutilizar en lugar de reescribir: la libft existe para esto. A cambio aparece una responsabilidad nueva, porque cada número impreso cuesta un malloc y alguien tiene que liberarlo; centralizar el free en un solo punto es la manera de no tener que pensar en ello en cada conversión. Y repasa la descomposición en cifras de C 00: la recursión vuelve a invertir el orden «de la última cifra a la primera» gratis, esta vez en cualquier base.

%x %X %pHexadecimal y punteros

Entrega: ft_print_hex.cAutorizado: write, malloc, free (+ libft: ft_itoa_base)
int	ft_print_hex(unsigned long n, int upper)
{
	char	*hex;

	if (upper)
		hex = "0123456789ABCDEF";
	else
		hex = "0123456789abcdef";
	return (ft_print_free(ft_itoa_base(n, hex, 16, 0)));
}

/* "0x" + la direccion en hex; NULL sale "(nil)", como en glibc. */
int	ft_print_ptr(void *p)
{
	int	ret;

	if (!p)
		return (ft_print_str("(nil)"));
	if (ft_print_str("0x") < 0)
		return (-1);
	ret = ft_print_hex((unsigned long)p, 0);
	if (ret < 0)
		return (-1);
	return (ret + 2);
}

La base no es un número sino una cadena de símbolos: la cifra k se escribe como base[k]. Cambiar de minúsculas a mayúsculas es cambiar de cadena; la misma ft_itoa_base sirve para base 10 y base 16.

ft_print_hex recibe un unsigned long aunque %x saque un unsigned int: es para que %p pueda reutilizarla. En Linux de 64 bits una dirección ocupa 8 bytes y no cabe en un unsigned int de 4; el unsigned int de %x se amplía sin pérdida al pasar. Así, con -1 sale ffffffff (el int reinterpretado como unsigned int), no ffffffffffffffff.

Para el puntero NULL el usuario imprime (nil), que es lo que hace glibc. Ojo: es un comportamiento propio de glibc; el printf de macOS imprime 0x0. Si el corrector prueba en otro sistema, el resultado esperado cambia.

Qué te obliga a aprender — Que un puntero es, al final, un número — una dirección — y que imprimirlo es imprimir ese número en base 16. De paso obliga a pensar en tamaños: int, unsigned int y unsigned long no son intercambiables, y elegir el tipo del parámetro (aquí, el más ancho) es lo que permite que una sola función sirva para dos conversiones. Y que «hexadecimal» no es nada especial: cualquier base es una tabla de símbolos más divisiones sucesivas.

makeEl Makefile y la libft

Entrega: Makefile, libft/Autorizado: ar (libtool prohibido)
NAME	= libftprintf.a

LIBFT_DIR	= libft
LIBFT	= $(LIBFT_DIR)/libft.a

SRCS	= ft_printf.c ft_print_chars.c ft_print_nbrs.c ft_print_hex.c
OBJS	= $(SRCS:.c=.o)

all: libft $(NAME)

libft:
	$(MAKE) -C $(LIBFT_DIR)

$(LIBFT): libft

$(NAME): $(OBJS) $(LIBFT)
	cp $(LIBFT) $(NAME)
	ar rcs $(NAME) $(OBJS)

%.o: %.c ft_printf.h $(LIBFT_DIR)/libft.h
	$(CC) $(CFLAGS) -c $< -o $@

El enunciado pide que, si usas la libft, la copies en un directorio libft/ con su propio Makefile, y que el Makefile del proyecto la compile primero. Eso hace la regla falsa (.PHONY) libft: delega con $(MAKE) -C libft, y es la libft la que decide si tiene algo que recompilar.

El truco está en la regla de $(NAME): copia libft.a con el nombre libftprintf.a y luego ar rcs le añade los objetos de ft_printf. Como un .a no es más que un archivo de .o, el resultado es una sola librería con todo dentro, y quien la use enlaza solo con -lftprintf. Sin esto, ft_print_str llamaría a un ft_strlen que no está en libftprintf.a y el enlazado fallaría.

Los .o dependen también de los dos headers, así que tocar ft_printf.h o libft.h recompila lo necesario. Ejecutar make dos veces seguidas solo vuelve a entrar en libft/ (que responde «Nothing to be done») y no relinka. clean y fclean también delegan en la libft.

Qué te obliga a aprender — Que una librería estática es un contenedor de objetos que se puede ampliar, y que las dependencias entre proyectos se resuelven con Makefiles que se llaman unos a otros (make -C), cada uno responsable de lo suyo. Es la primera vez que la libft deja de ser un proyecto aislado y pasa a ser una pieza que otro proyecto consume, que es para lo que existe.
