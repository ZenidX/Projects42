Cursus — Python Module 00 rank 02

«Growing Code»: el primer contacto con Python después de todo el C. Ocho ejercicios ambientados en un huerto comunitario que recorren lo básico — print, input, conversión con int, condicionales, bucles, recursión y, al final, anotaciones de tipo.

  • ex0 — ft_hello_garden
  • ex1 — ft_garden_name
  • ex2 — ft_plot_area
  • ex3 — ft_harvest_total
  • ex4 — ft_plant_age
  • ex5 — ft_water_reminder
  • ex6 — ft_count_harvest
  • ex7 — ft_seed_inventory
De C a Python — Después de la piscine, Libft, printf y push_swap, todo era memoria a mano: malloc, free, punteros, write byte a byte y una Norma que vigila cada línea. Python le da la vuelta a casi todo. No se compila: el intérprete python3 lee y ejecuta. Las variables no tienen tipo, lo tienen los valores (tipado dinámico), y la memoria la gestiona el recolector de basura: no hay malloc ni free, ni segfaults. En lugar de la norminette, el enunciado exige flake8 (el estilo PEP 8: sangría de 4 espacios, dos líneas en blanco entre definiciones, sin espacios al final de línea…) y, en el último ejercicio, mypy para comprobar los tipos. Una regla curiosa del módulo: cada fichero debe contener solo la función, sin código suelto ni bloque if __name__ == "__main__":; para probarlas se usa el main.py que da el enunciado, que las importa y las llama. Todo el repo pasa flake8 y mypy sin avisos.

ex0ft_hello_garden

Entrega: ft_hello_garden.pyAutorizado: print()
def ft_hello_garden():
    print("Hello, Garden Community!")

Dos líneas. def define la función, los dos puntos abren el bloque y la sangría marca qué hay dentro: no hay llaves ni punto y coma. print añade el salto de línea por su cuenta.

Qué te obliga a aprender — Que en Python la sangría es sintaxis. En C la Norma te exigía tabular bien por estética; aquí, si la línea del print no está sangrada, el programa ni arranca (IndentationError). Y que print no es write: ni descriptor, ni longitud, ni "\n" a mano.

ex1ft_garden_name

Entrega: ft_garden_name.pyAutorizado: input(), print()
def ft_garden_name():
    garden_name = input("Enter garden name: ")
    print(f"Garden: {garden_name}")
    print("Status: Growing well!")

input muestra el texto que se le pasa, espera a que el usuario pulse Intro y devuelve lo escrito como cadena (sin el salto de línea). Luego una f-string: la f delante de las comillas permite meter variables entre llaves.

Qué te obliga a aprender — Leer de la entrada estándar sin read, sin buffer de tamaño fijo y sin preocuparte de cuánto escribirá el usuario: la cadena crece lo que haga falta. Y las f-strings, que hacen en una línea lo que en C pedía printf("%s", ...) — o tu propio ft_printf entero.

ex2ft_plot_area

Entrega: ft_plot_area.pyAutorizado: input(), int(), print()
def ft_plot_area():
    length = int(input("Enter length: "))
    width = int(input("Enter width: "))
    area = length * width
    print(f"Plot area: {area}")

input siempre devuelve texto; para multiplicar hay que convertirlo con int(). Si el usuario escribe algo que no es un número, Python lanza una excepción y se para:

Enter length: a
ValueError: invalid literal for int() with base 10: 'a'

El enunciado dice explícitamente que no hace falta validar la entrada, así que es el comportamiento esperado.

Qué te obliga a aprender — Que tipado dinámico no significa «sin tipos». "5" * "3" es un error y "5" * 3 da "555": los valores tienen tipo y Python lo respeta con rigor. int() es tu ft_atoi, pero en vez de devolver basura ante una entrada rara, protesta. Y los enteros de Python no desbordan: crecen sin límite, adiós a INT_MAX.

ex3ft_harvest_total

Entrega: ft_harvest_total.pyAutorizado: input(), int(), print()
def ft_harvest_total():
    a = input("Day 1 harvest: ")
    b = input("Day 2 harvest: ")
    c = input("Day 3 harvest: ")
    total_harvest = int(a) + int(b) + int(c)
    print(f"Total harvest: {total_harvest}")

Aquí la conversión se hace al final, en la suma, en lugar de al leer como en ex2. Las dos formas valen; la diferencia es cuándo existe la variable como texto y cuándo como número.

Qué te obliga a aprender — Que una misma variable no tiene un tipo fijo declarado: a guarda una cadena, y es int(a) quien produce un valor nuevo de tipo entero. Fíjate también en que + entre cadenas concatena: a + b + c sin los int daría "583", no 16.

ex4ft_plant_age

Entrega: ft_plant_age.pyAutorizado: input(), int(), print()
def ft_plant_age():
    age = int(input("Enter plant age in days: "))
    if age > 60:
        print("Plant is ready to harvest!")
    else:
        print("Plant needs more time to grow.")
Qué te obliga a aprender — El if/else de Python: sin paréntesis obligatorios, con dos puntos y sangría. Y leer el enunciado con lupa, como en C00 con el cero de ft_is_negative: «estrictamente más de 60 días» es >, no >=. Con 60 exactos la planta todavía no está lista.

ex5ft_water_reminder

Entrega: ft_water_reminder.pyAutorizado: input(), int(), print()
def ft_water_reminder():
    a = input("Days since last watering: ")
    if int(a) > 2:
        print("Water the plants!")
    else:
        print("Plants are fine")

El mismo esquema que ex4, con la conversión hecha dentro de la condición.

Qué te obliga a aprender — Que comparar sin convertir no funciona: "4" > 2 lanza un TypeError porque Python no compara texto con números. En C, comparar un char * con un int compilaba (con suerte con un aviso) y comparaba una dirección de memoria; Python prefiere fallar en voz alta.

ex6ft_count_harvest

Entrega: ft_count_harvest_iterative.py, ft_count_harvest_recursive.pyAutorizado: input(), int(), print(), range(), funciones auxiliares para la recursión

Contar de 1 a n y terminar con «Harvest time!», dos veces: con un bucle y con recursión.

Versión iterativa

def ft_count_harvest_iterative():
    days = int(input("Days until harvest: "))
    for day in range(1, days + 1):
        print(f"Day {day}")
    print("Harvest time!")

El for de Python no es el de C: no tiene inicialización, condición y avance, sino que recorre los valores que le da range(1, days + 1), que va de 1 a days (el final no se incluye, de ahí el + 1).

Versión recursiva

def ft_count_harvest_recursive(days=None):
    is_first_call = False
    if days is None:
        day = int(input("Days until harvest: "))
        is_first_call = True
    else:
        day = days
    if day > 0:
        ft_count_harvest_recursive(day - 1)
        print(f"Day {day}")
    if is_first_call:
        print("Harvest time!")

Usa una de las opciones que propone el enunciado: un parámetro con valor por defecto. La llamada desde main.py no pasa argumentos, así que days vale None: es la primera llamada, la única que pide el número y la única que imprime «Harvest time!» al final. Las llamadas recursivas reciben ya el número.

El truco del orden es el mismo de ft_putnbr en C00: la función baja primero hasta 0 y luego, al volver, imprime. Así la pila de llamadas da la vuelta al orden y sale Day 1, Day 2… aunque se empiece por n.

Days until harvest: 5
Day 1
Day 2
Day 3
Day 4
Day 5
Harvest time!

Ojo: Python limita la profundidad de recursión (por defecto, unas 1000 llamadas). Con 990 días funciona; con 1000 la versión recursiva se para con RecursionError: maximum recursion depth exceeded, mientras la iterativa sigue sin problema. Para el enunciado no importa, pero es una diferencia real entre las dos versiones.

Qué te obliga a aprender — La comparación directa entre iteración y recursión, ahora en un lenguaje que las trata distinto que C. En C la recursión solo está limitada por el tamaño de la pila y, si te pasas, segfault; Python pone un tope explícito y lanza una excepción legible. También introduce dos piezas propias de Python: los parámetros por defecto y None, el «no hay valor» que sustituye a NULL (y que se compara con is, no con ==).

ex7ft_seed_inventory

Entrega: ft_seed_inventory.pyAutorizado: print(), métodos de cadena

El único ejercicio que recibe parámetros en lugar de leerlos, y el único con anotaciones de tipo obligatorias (la firma la da el enunciado).

def ft_seed_inventory(seed_type: str, quantity: int, unit: str) -> None:
    if unit == "packets":
        unit = "packets available"
        covers = ""
    elif unit == "grams":
        unit = "grams total"
        covers = ""
    elif unit == "area":
        unit = "square meters"
        covers = "covers "
    else:
        print("Unknown unit type")
        return
    print(f"{seed_type.capitalize()} seeds: {covers}{quantity} {unit}")

La cadena if/elif/else prepara dos trozos de texto — el sufijo y un posible prefijo «covers » — y un único print final los compone. La unidad desconocida sale antes con return. Comparar cadenas con == funciona directamente: nada de ft_strcmp. capitalize() es un método del propio objeto cadena: pone la primera letra en mayúscula.

>>> ft_seed_inventory("tomato", 15, "packets")
Tomato seeds: 15 packets available
>>> ft_seed_inventory("carrot", 8, "grams")
Carrot seeds: 8 grams total
>>> ft_seed_inventory("lettuce", 12, "area")
Lettuce seeds: covers 12 square meters
>>> ft_seed_inventory("x", 1, "kg")
Unknown unit type

Un detalle: el parámetro unit se reutiliza para guardar el texto de salida. Funciona porque es una variable local; mypy no protesta porque sigue siendo un str.

Qué te obliga a aprender — Las anotaciones de tipo: la vuelta de los tipos de C, pero opcionales y sin efecto en tiempo de ejecución. Python ignora : int al ejecutar — puedes pasar una cadena y nadie se queja —; es mypy quien las lee y avisa antes de ejecutar, como haría un compilador. Y los métodos: en Python todo es un objeto, y una cadena trae sus propias funciones ("lettuce".capitalize()), un anticipo de la orientación a objetos del módulo siguiente.
