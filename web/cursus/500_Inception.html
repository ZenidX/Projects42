De dónde viene — Born2beroot enseñaba a montar una máquina virtual y administrarla. Inception da el siguiente paso de la historia de la administración de sistemas: en lugar de una máquina por servicio, un único sistema que ejecuta varios servicios aislados entre sí con contenedores. Un contenedor no es una máquina virtual: no emula hardware ni arranca otro núcleo, sino que es un proceso normal del mismo kernel al que Linux le da una vista propia del sistema (sus propios namespaces de procesos, red y ficheros) y unos límites de recursos (cgroups). Docker (2013) popularizó la idea empaquetando esos mecanismos con un formato de imagen por capas y una receta reproducible, el Dockerfile; docker compose añadió la descripción de varios contenedores, sus redes y volúmenes en un único fichero YAML. Inception existe desde hace años en el common core; aquí se describe la versión 5.3 del enunciado, la que circula en 2026 y que ya incluye las instrucciones sobre IA y los ficheros de documentación. No se ha podido confirmar si 42next tiene una versión propia distinta.

01Contenedores e imágenes propias

La regla central es que tú construyes las imágenes: partes de una base mínima de Alpine o Debian e instalas y configuras el servicio encima. Nada de usar la imagen oficial de WordPress o de MariaDB. El enunciado añade dos prohibiciones que dicen mucho de lo que quiere que entiendas: no vale network: host, --link ni links:, y ningún contenedor puede arrancar con un bucle infinito (tail -f, bash, sleep infinity, while true), ni directamente ni dentro de un script de entrada.

Qué te obliga a aprender — Qué es el PID 1. Dentro de un contenedor, el proceso que lanzas es el proceso 1 de su espacio de procesos: el contenedor vive mientras viva él. Si ese proceso es un servicio que se va a segundo plano (un daemon clásico), el contenedor se queda sin proceso principal y se para; por eso la tentación es «sujetarlo» con un tail -f. El enunciado lo prohíbe porque es un parche: el proceso que de verdad importa no es el que Docker vigila, no recibe las señales de parada y si muere nadie se entera. La idea es que el servicio corra en primer plano como proceso principal. Además el PID 1 tiene responsabilidades especiales en Unix (recoger hijos huérfanos, tratar señales), que es lo que el enunciado te invita a leer.

02Los tres servicios

  • NGINX, solo con TLSv1.2 o TLSv1.3. Es la única puerta de entrada a la infraestructura, por el puerto 443 únicamente.
  • WordPress + php-fpm, instalado y configurado, sin nginx dentro.
  • MariaDB, sin nginx dentro.
  • En la base de datos de WordPress tiene que haber dos usuarios, uno de ellos administrador, y el nombre del administrador no puede contener «admin» ni «administrator» en ninguna variante.
Qué te obliga a aprender — La arquitectura clásica de una web dinámica partida en piezas. NGINX es un servidor web y proxy inverso: recibe la petición HTTPS, descifra TLS y, para lo que es PHP, se lo pasa a php-fpm por el protocolo FastCGI. php-fpm («FastCGI Process Manager») mantiene un grupo de procesos PHP listos para ejecutar el código de WordPress, que a su vez habla con MariaDB (un fork de MySQL nacido en 2009) por la red interna. Separarlos en contenedores obliga a entender qué habla con qué, por qué puerto y con qué protocolo, cosa que en una instalación «todo en uno» queda escondida. TLS es el sucesor de SSL; limitarlo a 1.2 y 1.3 deja fuera las versiones antiguas con debilidades conocidas.

03Volúmenes y red

  • Un volumen para la base de datos y otro para los ficheros de la web.
  • Deben ser volúmenes con nombre de Docker, no bind mounts, y sus datos tienen que quedar en /home/login/data en la máquina anfitriona.
  • Una red de Docker que conecte los contenedores; la línea de red tiene que aparecer en el docker-compose.yml.
Qué te obliga a aprender — Que un contenedor es efímero: lo que escribe en su propio sistema de ficheros desaparece cuando se recrea. Los datos que deben sobrevivir (la base de datos, los ficheros subidos) viven fuera, en volúmenes. La diferencia entre un volumen con nombre (lo gestiona Docker) y un bind mount (montas una ruta concreta del anfitrión) es una de las comparaciones que el README tiene que explicar. Con la red pasa igual: en una red de Docker los contenedores se encuentran por el nombre del servicio, como si hubiera un DNS interno, y solo lo que publicas hacia fuera (aquí, el 443 de NGINX) es accesible desde el anfitrión.

04Variables, .env y secretos

  • Ninguna contraseña en los Dockerfiles.
  • Uso obligatorio de variables de entorno y de un fichero .env (en el ejemplo, dentro de srcs/).
  • Muy recomendado usar Docker secrets para lo confidencial; el ejemplo de estructura tiene una carpeta secrets/ con ficheros de credenciales.
  • Cualquier credencial, clave o contraseña que aparezca en el repositorio Git (fuera de secretos bien configurados) supone suspender el proyecto.
Qué te obliga a aprender — A separar la configuración del código, una de las ideas de la metodología twelve-factor: la misma imagen tiene que servir con otras contraseñas sin reconstruirla. Y la diferencia entre una variable de entorno (visible para cualquiera que inspeccione el contenedor o sus procesos) y un secreto (un fichero montado solo donde hace falta). El README tiene que comparar ambos.

05README, USER_DOC y DEV_DOC

El README sigue el formato común de los enunciados nuevos (primera línea en cursiva con los logins, secciones Description, Instructions y Resources con el uso de IA) y además debe explicar el uso de Docker, las decisiones de diseño y cuatro comparaciones: máquinas virtuales frente a Docker, secretos frente a variables de entorno, red de Docker frente a red del anfitrión y volúmenes frente a bind mounts.

Para validar hacen falta también:

  • USER_DOC.md: qué servicios ofrece la pila, cómo arrancarla y pararla, cómo entrar a la web y al panel de administración, dónde están las credenciales y cómo comprobar que todo funciona.
  • DEV_DOC.md: cómo montar el entorno desde cero, construir y lanzar con el Makefile y compose, qué comandos usar para contenedores y volúmenes, y dónde se guardan y persisten los datos.

bonusServicios extra

Cada servicio extra con su propio Dockerfile y contenedor: caché Redis para WordPress, servidor FTP apuntando al volumen de la web, una web estática en cualquier lenguaje salvo PHP, Adminer y un servicio a tu elección que haya que justificar. Solo se evalúa si la parte obligatoria está perfecta.

Puntos delicados

  • El orden de arranque. WordPress necesita que MariaDB esté lista, no solo arrancada; «el contenedor existe» y «el servicio acepta conexiones» son cosas distintas.
  • La primera ejecución frente a las siguientes. Con volúmenes persistentes, la configuración inicial (crear la base de datos, los usuarios, instalar WordPress) no puede repetirse a ciegas en cada arranque.
  • «Penúltima versión estable» cambia con el tiempo: hay que comprobarla cuando se haga el proyecto y no copiarla de un repo antiguo.
  • Los secretos en Git. Un .env o una carpeta secrets/ subidos por descuido son suspenso directo; el .gitignore va antes del primer commit.
  • Nada de parches para mantener vivo el contenedor (ver PID 1), ni red host ni links.
  • El dominio login.42.fr tiene que resolver a la IP local dentro de la VM.
