Cursus — Libft

El primer proyecto del common core: una librería estática, libft.a, con 43 funciones escritas a mano. Media libc rehecha desde cero, once utilidades nuevas para cadenas y descriptores, y una lista enlazada genérica con t_list — todo empaquetado con un Makefile y ar.

  • is* / to* — clasificar caracteres
  • strlen, strchr, strrchr
  • strncmp, strnstr
  • strlcpy / strlcat
  • memset, bzero, memcpy, memchr, memcmp
  • memmove y el solapamiento
  • atoi
  • calloc / strdup
  • substr / strjoin
  • strtrim
  • split
  • itoa y el INT_MIN
  • strmapi / striteri
  • put*_fd
  • lstnew, lstadd_front, lstsize, lstlast
  • lstadd_back
  • lstdelone, lstclear, lstiter
  • lstmap y la liberación si falla
  • Makefile y librería estática
Por qué una librería propia — En casi todos los proyectos de C del cursus las funciones de la libc están prohibidas salvo un puñado (malloc, free, write…). Libft es la respuesta: escribes tú strlen, memcpy o split una vez, bien, y a partir de ahí las enlazas en ft_printf, get_next_line o push_swap. El enunciado (versión 19.3, camino 42next) la divide en tres partes obligatorias: Parte 1, funciones de la libc con el mismo prototipo y el mismo comportamiento que dice su man, pero con prefijo ft_; Parte 2, funciones adicionales que no están en la libc o están de otra forma; y Parte 3, listas enlazadas. En esta versión las ft_lst* ya no son bonus: son funciones normales, en ficheros ft_lstX.c, compiladas por el make de siempre. Las reglas técnicas pesan tanto como el código: nada de variables globales, auxiliares siempre static, todo en la raíz del repo, -Wall -Wextra -Werror, ar obligatorio (libtool prohibido), cero leaks y ningún segfault fuera del comportamiento indefinido. Y un README.md con descripción, instrucciones, recursos y uso de IA, que este repo incluye.

Parte 1 — Funciones de la libc

is* / to*isalpha, isdigit, isalnum, isascii, isprint, toupper, tolower

Entrega: ft_isalpha.c … ft_tolower.cAutorizado: ninguna

Siete funciones de una comparación. Todas reciben un int (no un char, para poder recibir EOF) y, según el enunciado, las de clasificación devuelven exactamente 1 o 0:

int	ft_isalpha(int c)
{
	if ((c >= 'A' && c <= 'Z') || (c >= 'a' && c <= 'z'))
		return (1);
	else
		return (0);
}

int	ft_isalnum(int c)
{
	if (ft_isdigit(c) || ft_isalpha(c))
		return (1);
	else
		return (0);
}

int	ft_toupper(int c)
{
	if (c >= 'a' && c <= 'z')
		return (c + 'A' - 'a');
	return (c);
}

ft_isprint usa el rango c > 31 && c < 127 (del espacio a la ~) y ft_isascii el 0..127. ft_isalnum reutiliza las otras dos en lugar de repetir los rangos. Ojo, una rareza de estilo: los cinco ft_is*.c incluyen <unistd.h> en vez de "libft.h", y ft_isalnum.c declara a mano los prototipos de ft_isalpha y ft_isdigit; compila igual, pero el resto del repo tira del header común.

Qué te obliga a aprender — Lo mismo que en C 02, pero ahora con el contrato de la libc: leer el man y respetar el tipo exacto (int, no char) y el valor de retorno exacto. El truco de c + 'A' - 'a' evita escribir el número 32 a pelo: expresa la distancia entre mayúsculas y minúsculas en términos de la propia tabla ASCII.

strstrlen, strchr, strrchr

Entrega: ft_strlen.c, ft_strchr.c, ft_strrchr.cAutorizado: ninguna
char	*ft_strchr(const char *s, int c)
{
	char	*p;

	p = (char *) s;
	while (*p != (char) c && *p)
		p++;
	if (*p == (char) c)
		return (p);
	return (NULL);
}

char	*ft_strrchr(const char *s, int c)
{
	char	*p;

	p = ((char *) s) + ft_strlen(s);
	while (*p != (char)c && p != s)
		p--;
	if (*p != (char) c && p == s)
		return (NULL);
	else
		return (p);
}

Dos detalles que pide el man y que el código cumple. El '\0' final cuenta como parte de la cadena: ft_strchr(s, '\0') devuelve un puntero al terminador, porque el bucle para en él y la comparación final acierta. Y c se convierte a (char) antes de comparar, así que ft_strchr(s, 'a' + 256) encuentra la 'a'. ft_strrchr va al revés: empieza en el terminador y retrocede hasta encontrar c o chocar con el principio.

Qué te obliga a aprender — El cast (char *) s es el primer choque con const: la libc recibe una cadena que promete no modificar pero devuelve un char * modificable dentro de ella. Es una decisión histórica del estándar (si devolviese const char * sería incómoda de usar con cadenas no constantes) y aquí te toca reproducirla tal cual.

cmpstrncmp, strnstr

Entrega: ft_strncmp.c, ft_strnstr.cAutorizado: ninguna
int	ft_strncmp(const char *s1, const char *s2, size_t n)
{
	size_t	i;

	if (n == 0)
		return (0);
	i = 0;
	while (s1[i] && s2[i] && s1[i] == s2[i] && i < n && i < n - 1)
		i++;
	if (i != n)
		return ((unsigned char) s1[i] - (unsigned char) s2[i]);
	return (0);
}

La resta se hace con unsigned char: el man exige comparar los bytes como sin signo, de modo que '\200' sea mayor que 'a' y no un número negativo. El bucle se detiene en n - 1 para que la última comparación sea la del carácter n-ésimo. Ojo, una rareza inofensiva: i < n sobra (lo implica i < n - 1) y, como el bucle nunca deja i == n, el return (0) final nunca se ejecuta.

	i = 0;
	while (p[i])
	{
		j = 0;
		while (i + j < len && q[j] && p[i + j] && p[i + j] == q[j])
			j++;
		if (!(q[j]))
			return (&p[i]);
		i++;
	}
	return (NULL);

ft_strnstr busca little dentro de los primeros len caracteres de big: por cada posición de salida intenta casar la aguja entera sin pasarse de len. Ojo: el bucle exterior solo para en el '\0' de big, no en len. El resultado es correcto (pasado len el bucle interior no avanza y nunca hay coincidencia), pero sigue leyendo big hasta su final; con un buffer que no tenga '\0' dentro de los len bytes, leería fuera.

Qué te obliga a aprender — Es la segunda vuelta de C 03 (strncmp, strstr), con dos matices nuevos: la comparación con unsigned char y el límite len. Las funciones "con n" de la libc existen para trabajar con memoria cuyo tamaño conoces, y el reto es que ese límite se respete en todas las lecturas, no solo en el resultado.

strl*strlcpy / strlcat

Entrega: ft_strlcpy.c, ft_strlcat.cAutorizado: ninguna

Las copias "seguras" de BSD: reciben el tamaño total del buffer destino (siz), nunca escriben más allá, siempre terminan en '\0' si hay sitio, y devuelven la longitud de la cadena que intentaron crear. Si el valor devuelto es >= siz, hubo truncado.

size_t	ft_strlcpy(char *dst, const char *src, size_t siz)
{
	size_t	i;

	if (siz == 0)
		return (ft_strlen(src));
	i = 0;
	while (i < siz - 1 && src[i])
	{
		dst[i] = src[i];
		i++;
	}
	dst[i] = '\0';
	return (ft_strlen(src));
}

El caso siz == 0 va primero por una razón concreta: siz es size_t, y siz - 1 con siz == 0 no da -1, da el size_t máximo — el bucle copiaría sin límite.

size_t	ft_strlcat(char *dst, const char *src, size_t siz)
{
	size_t	n_dst;
	size_t	i;

	n_dst = 0;
	while (n_dst < siz && dst[n_dst])
		n_dst++;
	if (n_dst == siz)
		return (siz + ft_strlen(src));
	n_dst = ft_strlen(dst);
	i = 0;
	while (i + n_dst < siz - 1 && src[i])
	{
		dst[n_dst + i] = src[i];
		i++;
	}
	dst[n_dst + i] = '\0';
	return (n_dst + ft_strlen(src));
}

ft_strlcat tiene la trampa famosa: si en los primeros siz bytes de dst no hay '\0', el destino "no cabe" y debe devolver siz + strlen(src) sin tocar nada. Por eso el primer bucle mide dst acotado por siz en lugar de llamar a ft_strlen sin más. Superado ese filtro se sabe que siz > n_dst, así que siz - 1 ya no puede dar la vuelta. Ejemplo: con dst = "abc", siz = 6 y src = "defghijkl" queda "abcde" y devuelve 12.

Qué te obliga a aprender — La aritmética sin signo como fuente de bugs: con size_t no existen los negativos, y cada resta hay que justificarla antes de escribirla. También el diseño del valor de retorno: devolver "lo que habría ocupado" permite detectar el truncado y reservar lo justo en un segundo intento. strlcpy ya apareció en C 02; aquí se le suma strlcat y el caso degenerado del destino lleno. El enunciado recuerda que glibc no las trae: para compararlas hace falta <bsd/string.h> y -lbsd.

memmemset, bzero, memcpy, memchr, memcmp

Entrega: ft_memset.c, ft_bzero.c, ft_memcpy.c, ft_memchr.c, ft_memcmp.cAutorizado: ninguna

Las mem* no saben nada de cadenas: trabajan con n bytes de memoria cualquiera, recibida como void *, y no se paran en ningún '\0'. Lo primero que hacen todas es convertir ese puntero genérico en unsigned char * para poder recorrerlo byte a byte:

void	*ft_memcpy(void *dest, const void *src, size_t n)
{
	unsigned char		*p;
	const unsigned char	*q;
	size_t				i;

	if (dest == NULL && src == NULL)
		return (dest);
	p = dest;
	q = src;
	i = 0;
	while (i < n)
	{
		p[i] = q[i];
		i++;
	}
	return (dest);
}

La guarda dest == NULL && src == NULL imita lo que hace la libc del sistema con dos punteros nulos (no hacer nada) y es la que suelen comprobar los testers. ft_memset y ft_bzero son el mismo bucle escribiendo (unsigned char) c o 0. En ft_memchr la condición i < n va antes que la lectura del byte, de modo que nunca toca p[n]:

	while (i < n && (unsigned char) p[i] != (unsigned char)c)
		i++;
	if (i == n)
		return (NULL);
	else
		return (&p[i]);
Qué te obliga a aprender — Que void * es "memoria sin tipo": no se puede desreferenciar ni hacer aritmética con él, hay que decidir cómo leerlo. Y que el orden de las condiciones de un && importa: la evaluación en cortocircuito es lo que garantiza que la comprobación del límite proteja la lectura. El README del propio repo menciona justo ese fallo (leer p[n] tras el bucle de memchr) entre los que hubo que corregir, y un test que coloca los buffers pegados a una página de memoria protegida para cazar lecturas fuera de rango.

memmovememmove y el solapamiento

Entrega: ft_memmove.cAutorizado: ninguna

memcpy no garantiza nada si origen y destino se solapan; memmove sí. El problema: si copias hacia delante y el destino empieza dentro del origen, machacas bytes que aún no has leído.

void	*ft_memmove(void *dest, const void *src, size_t n)
{
	unsigned char		*p;
	const unsigned char	*q;
	size_t				i;

	if (dest == NULL && src == NULL)
		return (NULL);
	p = dest;
	q = src;
	if (dest > src)
	{
		i = n;
		while (i > 0)
		{
			i--;
			p[i] = q[i];
		}
	}
	else
		return (ft_memcpy(dest, src, n));
	return (dest);
}

La solución es elegir el sentido de la copia. Si dest está por detrás de src, copiar de delante hacia atrás es seguro y se delega en ft_memcpy. Si dest está por delante, se copia de atrás hacia delante: el último byte primero, así los que se sobrescriben ya se han leído. Con "123456" y ft_memmove(m + 1, m, 4) sale "112346"; un memcpy ingenuo daría "111116". El patrón i = n; while (i > 0) { i--; … } evita el clásico while (i >= 0), que con size_t sería un bucle infinito.

Qué te obliga a aprender — A visualizar la memoria como una tira de bytes donde dos "variables" pueden ser trozos de la misma tira. Es la primera vez que el orden de un bucle cambia el resultado y no solo el rendimiento. (Comparar punteros con > solo está garantizado por el estándar dentro del mismo objeto; en la práctica todas las implementaciones de memmove hacen esto mismo.)

atoift_atoi

Entrega: ft_atoi.cAutorizado: ninguna

Espacios (incluidos \t \n \v \f \r, del 9 al 13), un único signo opcional y dígitos. malloccalloc / strdup

Entrega: ft_calloc.c, ft_strdup.cAutorizado: malloc
void	*ft_calloc(size_t nmemb, size_t size)
{
	void	*p;
	long	s;

	if (nmemb == 0 || size == 0)
		return (malloc(0));
	s = nmemb * size;
	if (nmemb != 0 && s / nmemb != size)
		return (NULL);
	p = (void *)malloc(sizeof(char) * s);
	if (!p)
		return (NULL);
	ft_bzero(p, nmemb * size);
	return (p);
}

calloc tiene dos responsabilidades además de poner a cero: (1) detectar que nmemb * size desborda — si al dividir el producto entre nmemb no sale size, la multiplicación dio la vuelta y se devuelve NULL en lugar de reservar un trozo diminuto; y (2) la regla que añade el enunciado: con nmemb o size a 0 debe devolver un puntero único que se pueda pasar a free. El código delega en malloc(0), que en glibc cumple eso (aunque el estándar permite que devuelva NULL). Ojo, una rareza: s es long y no size_t; la comprobación funciona igual porque en s / nmemb el long se convierte a size_t, pero el tipo natural sería size_t. El nmemb != 0 es redundante tras el primer if.

ft_strdup es el de C 07: ft_strlen, malloc(l + 1), comprobar NULL, copiar y cerrar con '\0'.

Qué te obliga a aprender — Que la multiplicación de enteros sin signo se desborda en silencio, y que un tamaño desbordado no da error sino una reserva demasiado pequeña seguida de un desbordamiento de buffer: un fallo de seguridad clásico. Y que "lo que dice el man" y "lo que hace tu sistema" no siempre coinciden — por eso el enunciado fija la regla del cero.

splitft_split

Entrega: ft_split.cAutorizado: malloc, free

La función más larga del proyecto, partida en cuatro auxiliares static. Dos pasadas sobre la cadena: una para contar palabras y reservar el array de punteros, otra para copiar cada palabra.

char	**ft_split(char const *s, char c)
{
	char	**r;
	size_t	n_str;

	n_str = ft_count_words(s, c);
	r = (char **)malloc(sizeof(char *) * (n_str + 1));
	if (!r)
		return (0);
	if (ft_add_word(s, r, c))
		return (r);
	else
		return (NULL);
}

Contar y copiar usan la misma máquina de dos estados: un indicador "estoy dentro de una palabra" que pasa a 1 al ver un carácter distinto de c y vuelve a 0 al ver c o el final. El bucle es while (1) con break después de procesar el '\0', para que la última palabra se cierre al llegar al terminador:

static int	ft_add_word(char const *s, char **r, char c)
{
	int	i[4];

	ft_bzero(i, sizeof(i));
	while (1)
	{
		if (s[i[0]] && s[i[0]] != c && i[1] == 0)
		{
			i[1] = 1;
			i[2] = i[0];
		}
		else if ((s[i[0]] == c || !s[i[0]]) && i[1] == 1)
		{
			i[1] = 0;
			r[i[3]] = ft_word_dup(s, i[2], i[0]);
			if (!r[i[3]])
				return (ft_free_split(r));
			i[3]++;
		}
		if (!s[i[0]])
			break ;
		i[0]++;
	}
	r[i[3]] = NULL;
	return (1);
}

Las cuatro variables van en un array int i[4] puesto a cero con ft_bzero: i[0] recorre la cadena, i[1] es el estado, i[2] marca dónde empezó la palabra e i[3] es el índice en el resultado. Es un recurso para que la función quepa en las 25 líneas de la Norma (cuatro declaraciones y cuatro inicializaciones se quedan en dos líneas), a costa de legibilidad.

static int	ft_free_split(char **r)
{
	int	i;

	i = 0;
	while (r[i])
	{
		free(r[i]);
		i++;
	}
	free(r);
	return (0);
}

La gestión del fallo es la parte que se evalúa: si un ft_word_dup devuelve NULL, ese mismo NULL ya está escrito en r[i[3]], así que ft_free_split libera exactamente las palabras anteriores, luego el array, y ft_split devuelve NULL sin fugas. Con " a bb ccc " y ' ' salen a, bb, ccc — separadores repetidos o en los extremos no generan palabras vacías.

Qué te obliga a aprender — Memoria en dos niveles: un array de punteros, cada uno a su propia reserva, que hay que liberar de dentro afuera. Y el principio de que si fallas a mitad, deshaces lo hecho: la función no puede devolver NULL dejando medio resultado colgado en el heap. Es el split de C 07 simplificado a un único separador, pero ahora con la liberación en caso de error como requisito explícito.

itoaft_itoa y el INT_MIN

Entrega: ft_itoa.cAutorizado: malloc

Una solución recursiva poco habitual: la recursión baja dígito a dígito contando la profundidad d, y es el caso base (el dígito más significativo) quien sabe ya cuántas cifras tiene el número y reserva la cadena. Al volver, cada nivel escribe su dígito en su posición.

static char	*ft_itoa_real(int n, int d)
{
	char	*r;
	int		dd;
	int		neg;

	neg = (n < 0);
	if (n / 10 != 0)
		r = ft_itoa_real(n / 10, d + 1);
	else
	{
		r = (char *)malloc(sizeof(char) * (d + 2 + neg));
		if (!r)
			return (NULL);
		r = ft_char_init(r, d + 1 + neg);
	}
	if (!r)
		return (NULL);
	dd = ft_strlen(r);
	if (neg)
	{
		r[0] = '-';
		r[dd - 1 - d] = -(n % 10) + '0';
	}
	else
		r[dd - 1 - d] = n % 10 + '0';
	return (r);
}

char	*ft_itoa(int n)
{
	return (ft_itoa_real(n, 0));
}

Si el número tiene d + 1 cifras, el caso base reserva d + 1 bytes más el signo más el '\0', y ft_char_init lo rellena de '0' para que ft_strlen(r) dé la longitud final desde el principio. El nivel de profundidad d escribe en r[dd - 1 - d]: el nivel 0 (las unidades) en la última posición, y así hacia la izquierda.

El INT_MIN se resuelve sin long: el número nunca se niega. Se divide tal cual, negativo, y en C99 n % 10 de un negativo es negativo (o cero), así que -(n % 10) es un dígito entre 0 y 9. Con -2147483648 la última cifra es -(-8) = 8 y no hace falta calcular +2147483648. Los casos 0, -5, INT_MAX e INT_MIN dan la cadena correcta. Un fallo de malloc en el caso base se propaga hacia arriba con los if (!r) return (NULL).

Qué te obliga a aprender — El mismo borde que el putnbr de C 00, pero ahora con memoria: hay que saber cuántas cifras tendrá el número antes de reservar. La mayoría lo resuelve con un bucle previo que cuenta dígitos; aquí la propia recursión hace de contador. Y la semántica de / y % con negativos (truncamiento hacia cero) deja de ser un detalle del estándar para convertirse en la herramienta que evita el desbordamiento.

Parte 3 — Listas enlazadas

El nodo — El enunciado da la estructura, que va en libft.h: 
typedef struct s_list
{
	void			*content;
	struct s_list	*next;
}					t_list;
Es la misma idea que el t_list de C 12 con otros nombres (content en lugar de data): un nodo que se apunta a sí mismo y un void * que permite guardar cualquier cosa. En la versión 42next estas nueve funciones forman parte de la parte obligatoria, como las demás; no hay ficheros _bonus ni regla bonus. Un cambio respecto a versiones anteriores del enunciado: ft_lstsize devuelve unsigned int, y así está en el código.

{

		return (NULL);
	else
	{

		n->next = NULL;

	}
}

void	ft_lstadd_front(t_list **lst, t_list *new)
{
	if (lst && new)
	{
		new->next = *lst;
		*lst = new;
	}
}

t_list	*ft_lstlast(t_list *lst)
{
	t_list	*n;

	n = lst;
	while (n && n->next != NULL)
		n = n->next;
	return (n);
}

Las cuatro piezas básicas. ft_lstnew no copia content: guarda el puntero tal cual. ft_lstadd_front recibe t_list ** porque tiene que cambiar la cabeza del llamante. ft_lstlast admite una lista vacía (devuelve NULL) gracias al n &&, y ft_lstsize es el recorrido canónico while (n) { n = n->next; i++; }.

Qué te obliga a aprender — Repaso de C 12: nodos en el heap, el doble puntero para modificar la cabeza y el recorrido hasta NULL. La novedad es que ahora la lista es tuya para todo el cursus: estas funciones van a sostener las pilas de push_swap.

lstft_lstadd_back

Entrega: ft_lstadd_back.cAutorizado: ninguna
void	ft_lstadd_back(t_list **lst, t_list *new)
{
	t_list	*n;

	if (!lst)
	{
		lst = &new;
	}
	else if (!(*lst))
	{
		n = NULL;
		*lst = new;
	}
	else
	{
		n = *lst;
		while (n->next != NULL)
			n = n->next;
		n->next = new;
	}
}

Tres casos: puntero a lista nulo, lista vacía (el nuevo nodo pasa a ser la cabeza) y lista con nodos (se camina hasta el último y se engancha). El comportamiento es correcto, pero ojo a dos líneas que no hacen nada: lst = &new; cambia la copia local del parámetro lst, que se pierde al salir de la función (el efecto real de esa rama es "no hacer nada", que es lo razonable), y n = NULL; asigna una variable que no se vuelve a usar. Además, como hay que recorrer la lista entera, añadir al final cuesta O(n).

Qué te obliga a aprender — Justo lo que ilustra esa línea muerta: un parámetro es una variable local. Para que un cambio se vea fuera hay que escribir a través del puntero (*lst = …), no reasignar el puntero mismo. Y que en una lista simple sin puntero a la cola, "el final" siempre está a n pasos.

lstlstdelone, lstclear, lstiter

Entrega: ft_lstdelone.c, ft_lstclear.c, ft_lstiter.cAutorizado: free (delone, clear) · ninguna (iter)
void	ft_lstdelone(t_list *lst, void (*del)(void *))
{
	if (lst && del)
	{
		del(lst->content);
		free(lst);
	}
}

void	ft_lstclear(t_list **lst, void (*del)(void *))
{
	if (lst && *lst && del)
	{
		if ((*lst)->next)
			ft_lstclear(&((*lst)->next), del);
		del((*lst)->content);
		free(*lst);
		*lst = NULL;
	}
}

Liberar un nodo son dos free distintos: el del contenido, que hace del porque solo el llamante sabe qué hay detrás del void *, y el del propio nodo. ft_lstclear está hecha con recursión: primero borra el resto de la lista desde el siguiente, luego el nodo actual, y deja el puntero del llamante a NULL como pide el enunciado. Así se evita el problema clásico de perder next al liberar un nodo. Ojo: cada nodo es un nivel de recursión, así que con una lista muy larga (cientos de miles de nodos) la pila podría desbordarse; una versión iterativa que guarde next antes de liberar no tiene ese límite.

ft_lstiter aplica f al contenido de cada nodo; el bucle se detiene en el último nodo y lo procesa aparte después, en lugar del más directo while (n) { f(n->content); n = n->next; }, con el mismo resultado.

Qué te obliga a aprender — La propiedad de la memoria cuando el contenedor no sabe qué contiene: la lista es dueña de sus nodos, pero el contenido lo libera una función que pone otro. Y el orden al destruir: nunca liberes algo de lo que todavía necesitas leer un campo. La recursión resuelve ese orden "gratis", a cambio de usar pila.

lstmapft_lstmap y la liberación si falla

Entrega: ft_lstmap.cAutorizado: malloc, free
t_list	*ft_lstmap(t_list *lst, void *(*f)(void *), void (*del)(void *))
{
	t_list	*r;
	t_list	*n;
	void	*content;

	if (!lst || !f)
		return (NULL);
	r = NULL;
	while (lst)
	{
		content = f(lst->content);
		n = ft_lstnew(content);
		if (!n)
		{
			del(content);
			ft_lstclear(&r, del);
			return (NULL);
		}
		ft_lstadd_back(&r, n);
		lst = lst->next;
	}
	return (r);
}

Construye una lista nueva aplicando f a cada contenido, sin tocar la original. Lo delicado es el camino de error. Si ft_lstnew falla, hay dos cosas en el aire: el content que f acaba de crear y que todavía no pertenece a ningún nodo (por eso se libera aparte con del(content)), y los nodos ya construidos en r, que ft_lstclear borra junto con sus contenidos. Guardar el resultado de f en una variable antes de crear el nodo es lo que permite liberarlo; la versión que hace ft_lstnew(f(lst->content)) en una línea lo pierde. El README del repo cuenta que una versión anterior tenía aquí un doble free.

Ojo a dos detalles. Se comprueba que f no sea NULL pero no del: si del es NULL y falla un malloc, la llamada del(content) se haría sobre un puntero nulo. Y como cada nodo se añade con ft_lstadd_back, que recorre r desde el principio, construir la lista cuesta O(n²); guardar un puntero al último nodo lo dejaría en O(n).

Qué te obliga a aprender — La regla que el enunciado repite en toda la Parte 2 y 3: si fallas a medias, no dejes nada colgado. Aquí obliga a llevar la cuenta de quién es dueño de cada trozo de memoria en cada instante, incluido el contenido "huérfano" que aún no está en ningún nodo. Es el mismo razonamiento que el ft_free_split de split, en una estructura enlazada.

Cada ft_*.c se compila por separado a su .o, y ar rcs los mete en un archivo: r inserta o reemplaza los objetos, c crea el archivo sin avisar y s escribe el índice de símbolos que usa el enlazador. libft.a depende de los .o y cada .o de su .c y de libft.h, así que un segundo make no recompila nada (no hay relink) y tocar el header recompila todo. Las listas van en SRCS como cualquier otra función: no hay regla bonus. libft.h lleva include guard (#ifndef LIBFT_H), el typedef de t_list y los 43 prototipos.

Para usarla, como explica el README: cc main.c -I. -L. -lft, donde -lft busca libft.a (o libft.so) en las rutas de -L.

Qué te obliga a aprender — Qué es de verdad una librería estática: un paquete de ficheros objeto con un índice, del que el enlazador copia en tu ejecutable solo los objetos que necesitas. Por eso la regla de "una función por fichero" tiene sentido: si usas ft_strlen, solo entra ft_strlen.o. Las dependencias del Makefile son lo que C 09 empezó y aquí se vuelve obligatorio: compilar solo lo que cambió.
