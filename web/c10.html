C Piscine — C 10

El módulo de los archivos y las llamadas al sistema. Se reimplementan utilidades de Unix (cat, tail, hexdump) usando solo open, read, write y close. Se aprende qué es un descriptor de fichero, cómo se gestionan los errores y los códigos de salida. 4 ejercicios (ex00–ex03).

  • ex00 — display_file
  • ex01 — cat
  • ex02 — tail
  • ex03 — hexdump
La introducción — El enunciado abre con una tanda de preguntas absurdas sacadas de ¿Qué pasaría si...? de Randall Munroe (el autor de xkcd): desde tirar un filete desde tan alto que se cocine al caer, hasta cuándo el ancho de banda de Internet superará al de una furgoneta de FedEx cargada de discos. La última pregunta — qué pasaría si todos los aspirantes al carnet respondieran al azar — es un guiño a la evaluación automática: la Moulinette no responde al azar, compara byte a byte.

ex00display_file

Entregable: Makefile + programaFunciones: open, read, write, close

Un programa ft_display_file que vuelca a la salida estándar el contenido del archivo que se le pasa. Sin malloc: buffer de tamaño fijo. Y con los errores exactos que pide el enunciado:

fd = open(argv[1], O_RDONLY);
if (fd < 0)
{
	ft_putstr_fd("Cannot read file.\n", 2);
	return (1);
}
while ((n = read(fd, buf, 4096)) > 0)
	write(1, buf, n);
close(fd);

Sin argumentos imprime File name missing.; con demasiados, Too many arguments.; si el archivo no se puede leer, Cannot read file. — todos por la salida de error y con salto de línea.

Descriptores de fichero y syscalls — Un descriptor de fichero (fd) es un simple entero con el que el kernel identifica algo abierto: un archivo, la terminal, un socket. Tres están abiertos siempre al arrancar: 0 es la entrada estándar, 1 la salida estándar, 2 la salida de error. open devuelve un fd nuevo (o -1 si falla); read copia bytes del fd a un buffer y devuelve cuántos leyó (0 = fin de archivo); write los vuelca a otro fd; close libera el descriptor. Estas son llamadas al sistema: no las resuelve tu programa, sino el núcleo del sistema operativo. Aquí, por primera vez, no se usa printf ni buffers automáticos: se habla con el disco directamente, en trozos de un buffer fijo, que es como funciona todo por debajo.

ex01cat

Entregable: Makefile + programaFunciones: open, read, write, close, strerror, basename

Un ft_cat que hace lo mismo que el cat del sistema: concatena los archivos que se le pasen (o lee de la entrada estándar si no hay ninguno) y, ante un archivo que falla, imprime un error con el formato de cat y sigue con el resto.

ft_cat: nofile: No such file or directory

El mensaje se construye con basename(argv[0]) (el nombre del programa), strerror(errno) (la descripción del error del sistema) y se escribe a la salida de error. El código de salida es 1 si algún archivo falló.

stderr vs stdout, errno y códigos de salida — La razón de tener dos salidas separadas es poder redirigir el resultado sin mezclarlo con los avisos: ft_cat *.txt > todo.txt manda el contenido al archivo (fd 1) mientras los errores siguen apareciendo en pantalla (fd 2). errno es una variable global que el sistema pone al fallar una llamada (por ejemplo, "no existe"); no es legible por sí sola, así que strerror(errno) la traduce a texto. basename recorta la ruta del programa a solo su nombre, para que el error diga ft_cat: y no la ruta entera. Y el código de salida (el return del main) es el canal por el que un programa le dice a la shell si fue bien (0) o mal (distinto de cero): eso es lo que encadenan los && del módulo de shell.

ex02tail

Entregable: Makefile + programaFunciones: + malloc, free

Un ft_tail que replica tail, gestionando solo la opción -c (los últimos N bytes). Con varios archivos, antepone la cabecera ==> nombre <== como el tail real.

$ ft_tail -c 5 archivo
$ ft_tail -c 3 a b
==> a <==
...
==> b <==
...

La solución mide primero el tamaño del archivo leyéndolo entero, calcula cuántos bytes saltar (tamaño − N), y en una segunda pasada escribe solo la cola. Acepta la opción pegada (-c5) o separada (-c 5).

Buffers y el problema de "los últimos N" — tail tiene una dificultad de fondo: para dar los últimos bytes hay que llegar primero al final, y un archivo se lee de principio a fin. Sin poder saltar directamente (aquí no se usa lseek), la vía es leer en bloques con un buffer fijo llevando la cuenta de la posición, y empezar a escribir solo cuando se cruza el umbral tamaño − N. Es el primer ejercicio que obliga a razonar sobre cuánto se ha leído y no solo qué: el buffer no es el archivo entero, es una ventana que se va deslizando. Que read pueda devolver menos bytes de los pedidos (y haya que llamarlo en bucle) es la lección que se arrastra desde ex00.

ex03hexdump

Entregable: Makefile + programaFunciones: + malloc, free

Un ft_hexdump que reproduce el hexdump del sistema (formato por defecto, sin opciones): el desplazamiento en hexadecimal y, por cada 16 bytes, grupos de dos bytes en hexadecimal.

$ ft_hexdump saludo.txt
0000000 6548 6c6c 206f 6f77 6c72 2164
000000c
Bytes, endianness y coincidir al byte — El formato por defecto de hexdump esconde un detalle revelador: cada grupo son dos bytes leídos como un número de 16 bits, y como la máquina es little-endian (el byte menos significativo va primero en memoria), los dos bytes salen con el orden invertido. Por eso "He" (bytes 48 65) se imprime 6548: el programa lee el par y lo muestra como una palabra, byte alto primero. Un byte suelto al final se completa con 00. El desplazamiento va en hexadecimal, y la línea final repite el total de bytes. Reproducir esto exactamente — incluido el relleno con espacios de la última línea para que quede alineada — es lo que hace que la salida coincida byte a byte con la herramienta real: la lección de fondo es que un archivo no es "texto", es una secuencia de bytes, y ver esos bytes en crudo es lo que permite entender formatos, cabeceras y los "números mágicos" del ft_magic de Shell 00.
