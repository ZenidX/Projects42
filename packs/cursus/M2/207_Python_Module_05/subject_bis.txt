Chapter I

Introduction

Welcome to the Alchemist’s Laboratory, young apprentice!

In medieval times, alchemists sought to transform base metals into gold. Today, as a
Python alchemist, you will learn to transform scattered code into organised, reusable
magical formulas. Just as ancient alchemists had their grimoires organised into chapters
and sections, Python code must be organised into modules and packages.

But no alchemist starts with the grimoire. First comes the laboratory itself: a workspace
sealed off from the outside world, so that a failed experiment never contaminates any-
thing beyond its own walls. Then come the reagents you bring in from elsewhere, and
the sigils that keep your secrets out of the pages anyone can read.

Only then can you write the formulas. And that is where the real mysteries begin:

   • Using __init__.py, the gateway that transforms a simple folder into a magical
     package

   • Choosing precisely what your package exposes, and what stays hidden

   • Calling the code of a distant module from a distant module

   • Managing absolute vs relative imports

   • Avoiding circular dependencies


In this codex you will build the whole laboratory, in order: the sealed workspace, the
reagent supply, the secret sigils, and finally the grimoire itself.


              Focus on understanding how these tools work, not just on making them
              work. A true alchemist understands every step of the transmutation
              process!

explore the various capabilities of AI tools and how they can support your work. How-
ever, always approach them with caution and critically assess the results. Whether it’s
code, documentation, ideas, or technical explanations, you can never be completely sure
that your question was well-formed or that the generated content is accurate. Your peers
are a valuable resource to help you avoid mistakes and blind spots.

   • You should develop the habit of systematically checking, reviewing, questioning,

   • You should always seek peer review — don’t rely solely on your own validation.

Before an apprentice is allowed to mix anything, they must seal the laboratory: an iso-
lated space where a botched experiment ruins only the experiment. In Python, that
sealed room is a virtual environment. Once it is sealed, the apprentice may finally
bring reagents in from the outside world without poisoning everything else they own; that
is dependency management.

This first exercise covers both halves of that preparation, because neither is useful alone.

The laboratory is sealed, stocked and configured. Time to write formulas.

Every alchemist starts with simple ingredients in their alembic. But some ingredients sit
close at hand, and others live deep inside a cupboard. This exercise is about the import
mechanisms that reach each of them, and about the gateway that decides what a package
shows to the outside world.

First, build the components of the laboratory architecture.

   elements.py (at the root of the repository) will contain:

   • A function create_fire() that just returns the string “Fire element created”.

   • A function create_water() that just returns the string “Water element created”.


   alchemy/elements.py will contain:

   • A function create_earth() that just returns the string “Earth element created”.

   • A function create_air() that just returns the string “Air element created”.


   alchemy/__init__.py will contain:

   • Whatever is needed to expose create_air through the alchemy package interface,
     and nothing that exposes create_earth . See ft_alembic_1.py .

The final mystery, and the one that destroys laboratories: the circular dependency,
which occurs when two modules try to summon each other in an endless loop.

You will write the same feature twice: once so that it works, and once so that it explodes.
The point is that the difference between the two is a single design decision, not a single
line of syntax.



The light grimoire, which survives
alchemy/grimoire/light_spellbook.py will contain:

   • A function light_spell_allowed_ingredients() that returns the list of ingredi-
     ents allowed for light magic: “earth”, “air”, “fire”, “water”.

   • A function light_spell_record(spell_name: str, ingredients: str) that re-
     turns a string stating whether the spell was recorded or rejected. That decision
     comes from the validator below.

   alchemy/grimoire/light_validator.py will contain:

   • A function validate_ingredients(ingredients: str) that returns a string con-
     taining the ingredients and the “VALID” or “INVALID” keyword. The ingredients
     are valid if they include at least one of the ingredients allowed by the spellbook,
     case insensitive.

Notice the shape of the problem: the spellbook needs the validator to decide, and the
validator needs the spellbook to know what is allowed. Each file needs the other. There
are several ways to keep that from exploding; pick one, and be ready to explain the
alternatives during the evaluation.

This time, write the mutual dependency the naive way, at the top of both files, and leave
