Chapter I

Introduction

Welcome to the Code Nexus, Stream Engineer!

The year is 2087. In the sprawling digital metropolis of Neo-Tokyo, data flows through
quantum fiber networks like neon-bright rivers of pure information. The Code Nexus
stands as humanity’s greatest achievement: a cybernetic cathedral where billions of data
streams converge, transform, and evolve in perfect harmony.

But the Nexus does not just consume data; it understands it. Each data stream carries
its own digital signature, its own behavioral patterns. How does a single system compre-
hend such diversity?

Through the principles of abstract classes, polymorphism, method overriding, and
inheritance hierarchies, you will handle different types of data in the same software
workflow.

You will build that understanding in two movements. First the foundations: an abstract
processor hierarchy, a stream that routes anything to whatever can handle it, and a plu-
gin system that accepts any exporter which merely behaves correctly.

Then the architecture. Deep inside the Nexus runs a combat sandbox, where synthetic
entities are simulated against each other to stress-test the engine. Those entities are
just another class hierarchy, and they will teach you the questions a foundation cannot
answer on its own: who is allowed to create an object, how do you bolt an extra ability
onto a type without corrupting its family tree, and how do you swap out an algorithm
at runtime without the calling code ever knowing.

Welcome to the future. Welcome to the Code Nexus.

Exercise 0: Data Processor

                                       Exercise0

                                    data_processor
   Files to Submit: data_processor.py
   Authorized: builtins, standard types, import typing, import abc



Engineering Briefing: Welcome to the Code Nexus! Build the foundation of our data
processing system. You will create the base processor architecture and demonstrate
how different data types can share common processing interfaces while maintaining their
unique characteristics.

This exercise requires the use of abstract classes using ABC (Abstract Base Class). We
will first create separate classes that share common interfaces. In the next exercise, they
will be unified in the same workflow.

Set up the following architecture:

   • An abstract class DataProcessor that inherits from ABC and defines the common
     processing interface.

   • Three specialized classes NumericProcessor, TextProcessor, and LogProcessor
     that inherit from the DataProcessor class and will process different kinds of data.

   • Two abstract methods in DataProcessor: validate, which will check whether the
     input data are appropriate for the current data processor, and ingest, which will
     process the input data. Each specialized class will need to override these methods.

   • One standard method in DataProcessor: output, which will output ingested data.


You need to comply with the following constraints:

   • The validate method will be defined as validate(self, data: Any) -> bool
     in the DataProcessor class. The overriding methods in the specialized classes will
     share the same signature, as they cannot know what data will be sent and must


                                            7
Code Nexus                Abstract Architecture, from Data Streams to Battle Strategies


      accept any type. This method returns a bool that indicates if the provided data
      can be ingested by this data processor.

   • The ingest method will be defined as ingest(self, data: Any) -> None in the
     DataProcessor class. The overriding methods in the specialized classes will have
     their own specific signatures to match the types they expect. In case the user
     does not validate the data before calling ingest, and provides invalid data, an
     exception must be raised.

   • The output method will be defined as output(self) -> tuple[int, str] in the
     DataProcessor class. There is no need to override it in the specialized classes.

   • The NumericProcessor ingests int, float, and lists of both types (including
     mixed-type lists). It then converts the data into strings and stores it internally
     (keeping each item separated), waiting to be extracted piece by piece using the
     output method. The overriding ingest method signature must reflect the accepted
     types.

   • The TextProcessor ingests str and lists of strings. It stores the data internally
     (keeping each item separated), waiting to be extracted piece by piece using the
     output method. The overriding ingest method signature must reflect the accepted
     types.

   • The LogProcessor ingests a dict of string key-value pairs, and lists of that type.
     It then converts the data into strings and stores it internally (keeping each item
     separated), waiting to be extracted piece by piece using the output method. The
     overriding ingest method signature must reflect the accepted types.

   • The output method will extract the oldest piece of data stored internally in the
     data processor, along with the associated processing rank within the data processor.
     The piece of data is then removed from the data processor.


Finally, test your architecture:

   • Create instances for each specialized class.

   • Test valid and invalid data for each class through the validate method.

   • Test at least one invalid data item with the ingest method without prior validation,
     and check that it raises an exception. This will leave you with a mypy warning, on
     purpose.

   • Ingest various data for each data processor and then extract it using output.

Use your code from Exercise 0 and improve it:

   • Create a test scenario that demonstrates the correct processing of a data stream.

   files in it

Engineering Briefing: you are moving from the data plane to the Nexus combat sand-
box, where synthetic entities are simulated against each other to stress-test the engine.

You already know how to write an abstract hierarchy: you built one in Exercise 0. This
exercise answers the two questions that hierarchy left open. First, who creates the
objects: entities come in families, they evolve, and the calling code should not have to
know which concrete class it is getting (the abstract factory pattern). Second, how to
give a type an ability without pretending that ability belongs to every entity in the
world (a capability kept as a separate abstract class).

In the ex3/ package, implement:
   • A Creature abstract class (inheriting from ABC) that holds attributes for the name
     and the type of the entity, an abstract method attack, and a concrete method
     describe that returns a standard message built from the name and the type.
   • Two plain concrete entities that inherit from Creature: Flameling and Pyrodon
     (their attack returns an appropriate message, see the example).
   • A TransformCapability abstract class (inheriting from ABC) defining the transform
     and revert abstract methods. It must not inherit from Creature: an ability
     should not be forced onto every entity. An attribute keeps the transformed state
     and changes what attack returns.
   • Two concrete entities that inherit from both Creature and TransformCapability:
     Shiftling and Morphagon.

   • A CreatureFactory abstract class (inheriting from ABC) with the create_base and
     create_evolved abstract methods.

   • Two concrete factories inheriting from CreatureFactory: FlameFactory (base
     Flameling, evolved Pyrodon) and TransformCreatureFactory (base Shiftling,
     evolved Morphagon).

   • Your ex3 package must only expose the factories, never the concrete entities.

Exercise 4: Abstract Strategy

                                        Exercise4

                                         ex4
   Files to Submit: tournament.py, ex4/ as a package with all needed files in it
   Authorized: builtins, standard types, import typing, import abc



As you saw in the previous exercise, an entity with a capability acts differently: a trans-
forming entity will transform, attack, then revert, while a plain entity just attacks.
The day we draw entities from different families and make them fight in a tournament,
we would need battle code aware of each capability. Or maybe not? Let’s use the abstract
strategy pattern.

In the ex4/ package, implement:

   • A BattleStrategy abstract class (inheriting from ABC) defining the act and is_valid
     abstract methods. is_valid returns a bool telling whether an entity is suitable
     for the strategy; act is called by the tournament.

   • Two concrete strategies inheriting from BattleStrategy:

        ◦ NormalStrategy, suitable for any entity, that simply calls attack.
        ◦ AggressiveStrategy, suitable for entities with the transform capability, that
          will transform, attack, then revert.

   • If act is called with an entity the strategy is not valid for, raise a dedicated exception
     with a clear message.


              A strategy checks capabilities with isinstance, never the concrete
              family. You may add more strategies, as long as one plain strategy
              and one capability-aware strategy are present.


The tournament.py script (at the root) then:

  • Defines a single battle function that takes a list of opponents, each a tuple of a
    CreatureFactory and a BattleStrategy, makes each opponent face every other
    one once, applies each entity’s strategy, and aborts on an invalid entity-strategy
    pair.
